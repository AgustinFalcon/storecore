# Technical specification — Phase 1 commercial coordination

## Boundaries

The feature is split into four modules: `notification`, `commercialcalendar`, `channelreporting` and `loyalty`. Domain packages import no Spring, HTTP, SQL or Angular. Application services depend on ports; infrastructure adapters own JDBC, clocks, UUIDs and external delivery.

## Closed domain types

Kotlin uses `enum class` or `sealed interface` for alert severity/category/lifecycle, calendar lifecycle/transition/audience, channel/source/freshness, report period state, loyalty unit/movement/reservation state and every command result. Angular uses private-token classes with canonical static instances and one `fromWire`; `Unknown` is always present. Labels and transition rules live in the type, never in view string switches.

Notification domain freezes these cases: severity `INFO|WARNING|CRITICAL|UNKNOWN`; category `STOCK|ORDER|PAYMENT|RETURN|INTEGRATION|CAMPAIGN|UNKNOWN`; lifecycle `OPEN|ACKNOWLEDGED|RESOLVED|UNKNOWN`; source `STORECORE_FACT|BLACKSTORE_STOCK_RECEIPT|SYSTEM_CAMPAIGN|UNKNOWN`. Transition step objects implement only acknowledge `OPEN -> ACKNOWLEDGED`, resolve `OPEN|ACKNOWLEDGED -> RESOLVED`, and reopen `RESOLVED -> OPEN`. Unknown has no actions. The aggregate increments a non-negative revision with checked arithmetic and never mutates source identity or fingerprint.

Calendar domain freezes lifecycle `DRAFT|SCHEDULED|ACTIVE|PAUSED|COMPLETED|CANCELLED|UNKNOWN`, audience `INTERNAL_ALL|UNKNOWN`, command `EDIT|SCHEDULE|PAUSE|RESUME|CANCEL|SYSTEM_ACTIVATE|SYSTEM_COMPLETE|UNKNOWN`, reminder channel `IN_APP|UNKNOWN`, occurrence state `PENDING|LEASED|EMITTED|SKIPPED|DEAD|UNKNOWN`, kill-switch state `DISABLED|ENABLED|UNKNOWN` and runner readiness `UNAVAILABLE|READY|UNKNOWN`. Create is its own application step and produces DRAFT. Edit is a definition step allowed only while DRAFT; it does not pretend to be a lifecycle transition. Each lifecycle command is a transition object that owns one rule from PCC-R10B; the aggregate orders those objects and does not switch on wire strings. Terminal and Unknown cases expose no transition. Calendar command results are closed `APPLIED|REVISION_CONFLICT|INVALID_TRANSITION|INVALID_DEFINITION|PREFLIGHT_REQUIRED|PREFLIGHT_EXPIRED|PREFLIGHT_STALE|REVISION_EXHAUSTED|UNKNOWN`.

## Persistence

- Notifications: append-only source events, current alert projection, command receipt and audit tables. Unique `(source_type, source_id, fingerprint)`.
- Calendar: event identity, revisioned definition, transition receipt and audit. Timestamps are instants; merchant timezone is a validated IANA identifier stored with the event.
- Reports: no duplicate business truth. Read models query authoritative StoreCore tables. Existing BlackStore receipts expose only stock/version/availability, never monetary facts. A future BlackStore commercial projection requires a separate reviewed contract and migration.
- Loyalty: append-only ledger, earning-lot allocation, recovery-pending adjustment and reservation records. Unique source/idempotency keys; balance uses checked integer arithmetic. No mutable balance column is authoritative. Reserve/commit/release/expire lock one customer ledger in PostgreSQL so availability is recalculated and mutated atomically.

Every migration supports clean install and upgrade from the current schema, has constraints equivalent to domain validation and preserves published checksums.

Calendar persistence stores the current event projection, immutable definition revisions, preflight snapshots, command receipts, transition audit, reminder rules, durable occurrences and one revisioned reminder-switch row. Aggregate `revision` is incremented by every applied definition or lifecycle command and is the compare-and-set token. `definition_revision` is incremented only by an applied draft edit; scheduling freezes it as `approved_definition_revision`. Both are non-negative signed 64-bit integers serialized over HTTP as canonical decimal text; increments use checked arithmetic and exhaustion fails closed. Definition hash is SHA-256 over one versioned length-framed UTF-8 tuple containing definition revision, title, description, resolved start/end instants, IANA zone, chosen offsets, audience, optional campaign reference and ordered reminder rules. Human labels, lifecycle revision and localized text are excluded from definition identity.

Calendar time input is the exact object `{localDateTime,timeZone,offset}`. `localDateTime` is ISO local date-time to whole seconds without zone, `timeZone` must exactly match an identifier published by the runtime IANA tzdb and must not be a short-id or fixed-offset form, and `offset` is `Z` or `±HH:MM`. The identifier is preserved exactly; the boundary does not guess or silently canonicalize tzdb links. It resolves all valid offsets for that local time: zero is a DST gap and invalid; one must equal the supplied offset; two require the supplied offset to select one. Persistence retains both resolved instant and original zone/offset. Server `Clock` owns now. Scheduling enforces the five-minute lead, 366-day horizon, 90-day duration and `[start,end)` window against the same transaction clock.

Notification ingestion treats the source delivery UUID and the logical episode identity independently. Replaying one delivery UUID with a different canonical event hash is a conflict. A different delivery for the same `(source_type, source_id, fingerprint)` appends source evidence but preserves the existing alert lifecycle, category and original severity; it never reopens, silently reclassifies or escalates the projection. A genuinely new severity policy or recurrence requires an explicit future command or a different producer-owned episode key.

Notification V1 bounds are shared by domain, HTTP and DDL: `source_id` 1..128 UTF-8 bytes; condition code 1..64 uppercase ASCII characters plus digits, `_`, `-` and `.`; episode key 1..128 UTF-8 bytes; lifecycle command reason 1..500 Unicode code points after trimming only ASCII space, tab, LF, CR, vertical tab and form feed from both edges; fingerprint exactly 64 lowercase hexadecimal characters. Every PostgreSQL `TEXT` value rejects `U+0000` in the domain before persistence. The producer passes a typed source identity and stable episode key. Fingerprinting uses SHA-256 over a versioned, length-prefixed UTF-8 sequence, never string concatenation. Event delivery identity, source identity, episode fingerprint and command payload hash are distinct value objects. Missing episode identity fails validation; time-bucket inference is forbidden.

## Commands and consistency

Every mutation derives the actor from the authenticated session and carries a command UUID and expected revision where applicable. A command key is scoped to operation, aggregate and actor and bound to a canonical payload hash. Replay requires current authorization and returns the prior receipt only for the same authority and payload; different content or aggregate fails closed. Receipt, effect and audit commit in one transaction. Calendar scheduling and alert lifecycle use compare-and-set. Loyalty flow is composed of independent quote, reserve, commit, release/reverse and reconcile step objects.

Calendar create carries a canonical non-zero command UUID and no client event id; the receipt returns the server event id, aggregate revision zero and definition revision zero. Before allocating an event id, create looks up the command UUID scoped to CREATE plus actor and canonical payload. An exact retry returns the original 201 receipt; different actor or payload is an idempotency conflict. `GET /api/v1/user/commercial-calendar/commands/{commandId}` lets the original ADMIN recover a lost create response without knowing the event id; foreign and absent commands are indistinguishable 404. Edit, schedule, pause, resume and cancel carry canonical command UUID, expected aggregate revision and bounded reason where applicable. EDIT also carries the target definition revision explicitly inside its definition; it is a separate token, must be the checked successor of the definition revision in the reviewed snapshot, and is never derived from aggregate revision or current state during replay. SYSTEM activation/completion use a separate internal authority and deterministic command identity derived from event, aggregate revision, transition and boundary instant. Every well-formed, currently authorized command against an existing aggregate persists an immutable typed receipt for `APPLIED`, `REVISION_CONFLICT`, `INVALID_TRANSITION`, `INVALID_DEFINITION`, `PREFLIGHT_REQUIRED`, `PREFLIGHT_EXPIRED`, `PREFLIGHT_STALE` or `REVISION_EXHAUSTED`. Effect, projection, receipt and audit commit atomically. Malformed, unknown, missing and unauthorized commands create no receipt. Exact replay first revalidates current authorization and returns the historical snapshot only to the original actor; a foreign actor and absent receipt are indistinguishable 404. Reusing a UUID with different actor, aggregate, operation or canonical payload is an idempotency conflict.

Preflight is a persisted, expiring snapshot, not UI state. It stores event id, aggregate revision, definition revision, definition hash, typed issue set, checked-at and expires-at from the server clock. Only a snapshot with no blocking issue may be explicitly approved by SCHEDULE. The scheduling transaction locks event and preflight, rechecks actor, both revisions, definition hash, expiry, five-minute lead and lifecycle, then applies aggregate-revision CAS. Any definition edit produces new aggregate and definition revisions plus a new hash and invalidates prior snapshots.

Reminder rules are ordered by stable rule id and unique offset. PCC-007 persists their contracts but starts no runner. PCC-008 may claim at most 50 due occurrences per transaction with a 60-second lease and at most three attempts. Durable uniqueness is `(event_id,approved_definition_revision,rule_id,scheduled_at)`. Immediately before creating the in-app CAMPAIGN alert, the worker locks/revalidates occurrence, switch `ENABLED`, the event's unchanged approved definition revision and its current eligible lifecycle. It also locks the current aggregate row so a concurrent pause/cancel must serialize, but lifecycle revision changes do not re-key an otherwise future occurrence. A disabled switch, changed definition or ineligible lifecycle commits `SKIPPED`; no effect is created. Handoff uses a stable notification episode key derived from occurrence identity, so a lost response cannot duplicate an alert. Retry is allowed only before the atomic notification insert; three proven failures become `DEAD`. More-than-15-minute-late work is `SKIPPED`, and resume creates no backlog.

PCC-002 persists immutable receipts for every well-formed, currently authorized notification lifecycle command against an existing aggregate, including `APPLIED`, `REVISION_CONFLICT`, `INVALID_TRANSITION` and `REVISION_EXHAUSTED`. The receipt stores the original typed result and historical snapshot; an exact replay returns that result even if the alert later changes, after authorization is checked again. Unknown/malformed commands, missing aggregates and unauthorized attempts do not create receipts. A command UUID reused with a different actor, aggregate, operation or canonical payload is always an idempotency conflict.

Loyalty policy is immutable and versioned on every quote/reservation. Policy V1 implements the functional numeric rules. Each reservation references its policy version and eligible-price snapshot. Reservation state is closed: `QUOTED`, `PAYMENT_PENDING`, `COMMITTED`, `RELEASED`, `UNKNOWN`. Creating the payment attempt and promoting `QUOTED` to `PAYMENT_PENDING` share one transaction; only `QUOTED` is TTL-expirable. Provider uncertainty remains held until reconciliation. PostgreSQL tests race two individually valid reservations whose sum exceeds availability; at most one commits, and another test crosses quote expiry with late payment approval without double spend.

Return processing stores cumulative eligible value returned plus prior earned-reversal and redeemed-restoration totals. Each partial return applies only the checked delta to the cumulative target, with exact original totals at 100%. Recovery-pending adjustments reduce future earn availability but never block or roll back an authoritative refund or return.

## HTTP and authorization

- Slice A notification reads allow `ADMIN` and `OPERATOR`; acknowledge, resolve and reopen allow `ADMIN` only. The application derives the actor and role from the live USER session on every command and replay.
- Notification HTTP V1 exposes `GET /api/v1/user/notifications`, `GET /api/v1/user/notifications/{alertId}`, `POST /api/v1/user/notifications/{alertId}/commands` and `GET /api/v1/user/notifications/{alertId}/commands/{commandId}`. List filters are optional closed severity/category/lifecycle/source values; an unknown supplied filter is invalid rather than absent. Pagination is zero-based, defaults to 25 and is capped at 100. Ordering is `created_at DESC,id ASC`; revision is serialized as a canonical unsigned decimal string.
- The command endpoint accepts exact fields `{operation,expectedRevision,reason}` plus a canonical non-zero UUID `Idempotency-Key`. It requires USER ADMIN, same-origin JSON and CSRF through the existing mutation coordinator. Business rejections and exact replay return the rotated CSRF token. Applied returns 200; domain conflicts return 409; malformed input 400; wrong media type 415; missing aggregate 404; corrupt/future persisted data 503. Every response is `Cache-Control: no-store`.
- Receipt lookup requires live USER ADMIN and the original actor; another actor and an absent or foreign aggregate are indistinguishable 404. OPERATOR reads alerts but cannot read receipt actor/reason details. Ingestion remains an internal port and is not exposed over HTTP.
- Calendar event reads allow USER ADMIN and OPERATOR. Create, preflight, schedule, edit, pause, resume, cancel, receipt recovery, audit and reminder-switch diagnostic read allow ADMIN only. SYSTEM transitions are internal application ports and have no public HTTP route. Every public request derives actor and role from the current USER session; client actor, role, recipient and user identifiers are rejected.
- PCC-007B HTTP exposes `GET /api/v1/user/commercial-calendar/events`, `GET /api/v1/user/commercial-calendar/events/{eventId}`, `POST /api/v1/user/commercial-calendar/events`, `GET /api/v1/user/commercial-calendar/commands/{commandId}` for create recovery, `POST /api/v1/user/commercial-calendar/events/{eventId}/preflights`, `POST /api/v1/user/commercial-calendar/events/{eventId}/commands`, `GET /api/v1/user/commercial-calendar/events/{eventId}/commands/{commandId}`, `GET /api/v1/user/commercial-calendar/events/{eventId}/audit` and ADMIN-only `GET /api/v1/user/commercial-calendar/reminder-switch`. It does not map `POST /api/v1/user/commercial-calendar/reminder-switch/commands`; that URL is 404 until PCC-008 closes the temporary kill-switch metadata, receipts, audit and activation gate required by `sdd/PATTERNS.md`. The diagnostic GET returns exact `{state,revision,readiness}` with readiness `UNAVAILABLE` in PCC-007B.
- Calendar list filters use optional closed lifecycle/audience values plus mandatory `from`/`to` instants, page and size. Unknown, additional or repeated parameters are invalid. Require `from < to`; the range is `[from,to)` and its duration is at most 366 × 86,400 seconds. Membership is strict overlap `start_at < to AND end_at > from`. Count and items use identical predicates in one database snapshot; ordering is `start_at ASC,id ASC`. Pagination is zero-based, defaults to 25 and is capped at 100; offset arithmetic uses `Long` and `hasMore` is `offset + items.size < total`. OPERATOR event DTOs exclude actor, reason, command receipt and private audit fields. Audit is ADMIN-only, accepts only page/size with the same defaults and caps, returns exact `{items,total,page,size,hasMore}`, and orders by `recorded_at ASC,command_id ASC` in one snapshot. An absent event is 404; an existing event without entries is an empty 200 page. Audit actor ids are positive decimal strings and SYSTEM actor is null; no session, cookie, token or CSRF material enters a DTO.
- Calendar mutation bodies are at most 32 KiB and exact: missing fields, duplicate keys, trailing tokens, invalid UTF-8, extra fields and explicit null outside the single allowed campaign reference are invalid. CREATE is `{definition}` and its definition revision is canonical decimal `"0"`. EDIT is `{operation,expectedRevision,reason,definition}` and the definition contains its explicit target `definitionRevision`; PREFLIGHT is `{expectedRevision}`; SCHEDULE is `{operation,expectedRevision,reason,preflightId}`; PAUSE, RESUME and CANCEL are `{operation,expectedRevision,reason}`. SCHEDULE is the explicit approval of the referenced canonical non-zero preflight UUID; a syntactically valid absent snapshot records `PREFLIGHT_REQUIRED`. SYSTEM, CREATE and Unknown operations are invalid on the event-command route. A definition is exact `{definitionRevision,title,description,start,end,audience,campaignReference,reminders}`: definitionRevision is a canonical non-negative signed-Long decimal string, description is required and may be empty, audience is exactly `INTERNAL_ALL`, campaignReference is required and may be null, reminders is required and may be an empty array of at most five unique ids and offsets, start/end are exact `{localDateTime,timeZone,offset}`, and each reminder is exact `{id,channel,offsetSeconds}` with a canonical non-zero UUID, `IN_APP` and integer offset 300..2,592,000.
- Calendar mutations require exact JSON fields, reject unknown fields, require same-origin JSON, CSRF and canonical non-zero `Idempotency-Key`, and use `Cache-Control: no-store`. Applied create is 201; other applied commands 200; recorded domain conflicts and exact replay are 409 or the original 2xx and always return the rotated CSRF token; malformed input 400; wrong media type 415; missing/foreign 404; unauthorized 403; corrupt/future persisted data 503. Receipt lookup is ADMIN plus original actor only and preserves 404 indistinguishability.
- Calendar Angular follows container -> view -> ComponentStore -> use case -> HTTP repository. Its domain owns private-constructor static types with one `fromWire` and `Unknown` for lifecycle, audience, operation, outcome, preflight issue, reminder channel, switch state/readiness, view mode, load state and command-recovery state. Aggregate and definition revisions remain canonical decimal strings and are never converted to JavaScript `number`. A sole mapper validates and correlates exact event, page, receipt, preflight, audit and switch DTOs; future finite values or corrupt structures produce a non-actionable unavailable state.
- Calendar routes are `/user/commercial-calendar`, `/user/commercial-calendar/new`, `/user/commercial-calendar/:eventId` and `/user/commercial-calendar/:eventId/edit`, with `new` registered before the identity parameter. The URL translator owns exact `view`, `month`, `zone`, `lifecycle`, `audience`, `page` and `size`; it derives API `from`/`to` instants from local month boundaries in the explicit IANA zone. Month and list consume one server page and expose its incompleteness rather than auto-fetching an unbounded month. Navigation back from detail restores applied URL state and focus.
- Calendar editor accepts whole-second local values, IANA zone and explicit offset for both boundaries. It never chooses an overlap offset or normalizes a gap silently. ADMIN review/preflight is bound to event id, aggregate revision, definition revision/hash, times/zones/offsets, audience, rules and expiry before schedule. OPERATOR code paths do not call audit, receipt, preflight or switch endpoints. UI SYSTEM operations are read-only history.
- The calendar command journal is USER actor/authentication-epoch scoped and stores the exact CREATE, EDIT, PREFLIGHT or lifecycle intent before POST. It conservatively locks on corrupt storage or uncertain transport. Lost CREATE uses `/commands/{commandId}` and lost event commands use the private event receipt route; a 404 is not proof of non-application, so exact POST replay remains available. Lost PREFLIGHT replays the exact POST and key. Responses are published only when actor generation plus command/event/operation/revision/payload correlation still match. Calendar POST routes are explicitly allowlisted for 409 CSRF rotation; no wildcard calendar exception is allowed.
- PCC-008A keeps `POST /reminder-switch/commands` unmapped, readiness `UNAVAILABLE`, capability unchanged and all scheduler/worker beans absent. PCC-008B must first close switch operation/receipt/audit DTOs, collision-safe singleton command identity in the global command UUID namespace, capability `ACTIVE`, expiry that fails closed and temporary metadata (`owner`, `reason`, `created_at`, `expires_at`, `removal_ticket`, affected action). PCC-008C closes bounded SYSTEM candidate selection plus the early-call-then-boundary regression. PCC-008D closes durable pause/disable suppression cutoffs, owner+attempt lease fencing, retry/backoff, failure classification and crash recovery. PCC-008E closes one-transaction notification insert plus occurrence `EMITTED` settlement for the stable `SYSTEM_CAMPAIGN/CAMPAIGN` identity. PCC-008F alone may wire activation after reviewed readiness evidence; switch ENABLE never promotes capability or readiness. PCC-008B..F are individually NO-GO until their exact contract, migration/writer and adversarial tests receive independent GPT-6.1 Sol approval for that cut; PCC-008F additionally requires an explicit activation GO.

### PCC-008B exact reminder-switch contract

The closed domain types are `CalendarSwitchOperation ENABLE|DISABLE|UNKNOWN`, configured `CalendarSwitchState ENABLED|DISABLED|UNKNOWN`, effectivity `EFFECTIVE|DISABLED|EXPIRED|UNKNOWN`, and outcome `APPLIED|REVISION_CONFLICT|INVALID_TRANSITION|CAPABILITY_NOT_ACTIVE|REVISION_EXHAUSTED|UNKNOWN`. One translator maps wire values at each HTTP/persistence boundary. Domain and application code never branch on raw strings.

The exact POST route is `/api/v1/user/commercial-calendar/reminder-switch/commands`; private recovery is `GET /api/v1/user/commercial-calendar/reminder-switch/commands/{commandId}` and immutable history is `GET /api/v1/user/commercial-calendar/reminder-switch/audit?page={page}&size={size}`. All three require a live USER ADMIN. POST requires same-origin JSON, CSRF, a canonical non-zero `Idempotency-Key`, a body no larger than 8 KiB and exact body `{operation,expectedRevision,owner,reason,expiresAt,removalTicket,affectedAction}`. `expectedRevision` is a canonical non-negative signed-Long decimal string. `affectedAction` is exactly `EMIT_IN_APP_CAMPAIGN_REMINDER`; timestamps are canonical whole-second UTC instants. Audit pagination is zero-based, defaults to 25, caps at 100 and orders `recorded_at ASC,command_id ASC` in one snapshot.

The switch read becomes exact `{configuredState,effectivity,revision,readiness,metadata}`. `metadata` is null only for the revision-zero bootstrap; otherwise it is exact `{owner,reason,createdAt,expiresAt,removalTicket,affectedAction}`. Readiness stays `UNAVAILABLE` in PCC-008B. The application derives effectivity from one authoritative clock: configured `DISABLED` is `DISABLED`; configured `ENABLED` before expiry is `EFFECTIVE`; configured `ENABLED` at/after expiry is `EXPIRED`; corrupt/future data maps to non-actionable `UNKNOWN`. Reads do not mutate the row, hide expiry or claim runner availability.

The shared historical snapshot DTO is exact `{configuredState,effectivity,revision,metadata}` with the same metadata shape and canonical decimal/timestamp serialization as the diagnostic read; effectivity is evaluated at the receipt's `recordedAt`, not at response time. POST and exact-replay GET return the same exact receipt DTO `{commandId,actorId,operation,outcome,expectedRevision,requestedMetadata,before,after,recordedAt}`. `requestedMetadata` has exact `{owner,reason,createdAt,expiresAt,removalTicket,affectedAction}` and preserves the attempted governance values even when a recorded domain rejection leaves `after == before`; its `createdAt` equals server-owned `recordedAt`. `commandId` is canonical UUID; `actorId`, `expectedRevision` and both snapshot revisions are canonical positive/non-negative decimal strings; before/after are non-null exact historical snapshots; `recordedAt` is a whole-second UTC instant. For a non-`APPLIED` recorded outcome `after` equals `before`; for `APPLIED`, `after.revision = before.revision + 1` and `after.metadata == requestedMetadata`. Neither DTO includes payload hash, session id, cookie, CSRF value, capability internals or transport credentials.

Audit returns exact `{items,total,page,size,hasMore}`. Each item is the same receipt DTO, ordered oldest first; `total`, `page` and `size` are JSON integers and `hasMore` uses absolute offset arithmetic. Because audit is ADMIN-only, it includes the positive decimal `actorId` and governance reason/owner contained in historical snapshots. Receipt recovery by a foreign actor or for an absent UUID returns the repository's indistinguishable generic 404 envelope. A global UUID collision or mismatched binding returns only generic `{code:"IDEMPOTENCY_CONFLICT"}` with no receipt, snapshots, actor, metadata or indication of the colliding family; POST CSRF rotation still follows the existing mutation coordinator.

Migration PCC-008B extends the singleton `calendar_reminder_switch` with nullable bootstrap governance columns and constraints: revision zero is exactly `DISABLED` with every governance column null; revision greater than zero requires all governance columns, fixed affected action and `expires_at>created_at`. Every applied mutation locks id `1`, increments revision exactly once, replaces the complete governance snapshot and is protected against deletion or any update outside the approved writer. `ENABLE` requires expiry in `(server_now+5 minutes, server_now+7 days]`; `DISABLE` accepts the same bounded governance window as an explicit review deadline, but its expiry can never re-enable delivery.

`calendar_command_bindings` adds family `REMINDER_SWITCH` while retaining one global `command_id` primary key. EVENT/PREFLIGHT bindings require an event id; REMINDER_SWITCH requires it null. A dedicated immutable `calendar_switch_command_receipts` row stores command id, actor, operation, expected revision, canonical requested metadata, canonical payload hash, outcome, before/after exact snapshots and recorded instant. `calendar_switch_audit` references every recorded switch receipt, including recorded domain rejections, so an attempted safety-state change and its requested governance metadata are never hidden. The canonical hash is length-framed over version `calendar-reminder-switch-v1`, actor id, operation, expected revision, owner, reason, canonical expiry, removal ticket and affected action; server-owned `createdAt` is deliberately excluded so exact retries retain the same identity. An exact replay first revalidates current ADMIN authorization and returns the historical result only to the original actor. A foreign actor or absent receipt is the same 404; any global UUID collision or mismatched binding is an idempotency conflict.

The writer order is normative: (1) authenticate and authorize the live USER ADMIN; (2) enforce exact structural/canonical shape and compute the canonical payload hash without applying a relative-to-now expiry rule; (3) resolve the global command binding. An existing exact family/actor/hash binding returns its immutable receipt before evaluating current expiry, singleton revision, transition, capability state or kill state. An existing mismatched binding returns the generic collision. Only a UUID with no binding proceeds to (4) validate its relative expiry and metadata, (5) lock/read the singleton, evaluate CAS/transition/capability and (6) atomically insert binding, receipt, audit and any applied singleton update. Concurrent first use uses the global unique key as the serialization boundary; a loser re-reads the committed binding and applies the same exact-replay/collision rules rather than emitting a second result.

`ENABLE` evaluates the existing capability engine in the same transaction after locking the singleton: module `COMMERCIAL_CALENDAR` must already be `ACTIVE`, action `EMIT_IN_APP_CAMPAIGN_REMINDER` must be registered as a write/publish action, and an effective capability kill denies. PCC-008B may reclassify the module from future-only so normal capability administration can set it, but the migration leaves its installed configuration `DISABLED`; the reminder command itself cannot change capability configuration. `DISABLE` bypasses capability admission only as a narrow safety command and still requires live ADMIN, CAS, CSRF, idempotency and audit.

Well-formed authorized requests against the singleton record `APPLIED`, `REVISION_CONFLICT`, `INVALID_TRANSITION`, `CAPABILITY_NOT_ACTIVE` or `REVISION_EXHAUSTED` atomically with the binding and receipt. Malformed/unknown metadata, missing singleton, unauthorized actor and corrupt persisted state fail without a receipt. Applied returns 200; recorded conflicts and idempotency conflicts return 409; malformed input 400; wrong media type 415; unauthorized 403; corrupt/future data 503. Every response is `Cache-Control: no-store` and every recorded response rotates CSRF consistently with existing calendar commands.

No scheduler, timer, background executor, occurrence claim, notification insert, external call, email projection or automatic capability/readiness transition is installed by PCC-008B. Adversarial tests must cover global UUID collision across all three families, foreign receipt recovery, parallel CAS, expired `ENABLE`, boundary instants, capability state/kill denial, safety `DISABLE` under each denied capability state, metadata bounds, revision exhaustion, immutable audit and absence of runner beans. Exact replay must additionally pass after its expiry, after singleton revision/state changes, after capability/kill changes and after the original actor loses then regains valid ADMIN authorization; replay while authorization is currently absent remains denied.

### PCC-008C exact bounded SYSTEM lifecycle contract

PCC-008C introduces no wire or HTTP type. Its closed application types are `CalendarSystemSelectionResult PAGE|CORRUPT`, `CalendarSystemAdvanceResult RECORDED|MISSING|CORRUPT`, `CalendarSystemReceiptDisposition NEW|REPLAY|UNKNOWN` and `CalendarSystemCycleResult COMPLETED|CORRUPT_SELECTION`; operations remain the existing closed `CalendarOperation SYSTEM_ACTIVATE|SYSTEM_COMPLETE|UNKNOWN`. `CalendarSystemBatchSize` accepts only 1..100 and defaults to 50. A candidate is immutable and retains the validated observed `CalendarEvent` snapshot plus derived `{operation,boundary,observedAt}`; `expectedRevision` is the snapshot revision. Its private/internal factory accepts only a decoded event and whole-second `observedAt`, derives completion or activation and its exact end/start boundary itself, and returns no candidate when the event is not due. Callers cannot supply or change operation, revision or boundary independently. Domain and application code never branch on raw lifecycle or operation strings.

`CalendarSystemCycleService.run(batchSize)` captures one authoritative UTC `observedAt`, truncated to whole seconds, before calling persistence or acquiring a lock. The candidate query uses that same value in every predicate and returns no more than `batchSize` rows. Eligibility is exact: `SYSTEM_COMPLETE` for lifecycle `SCHEDULED|ACTIVE|PAUSED` when `end_at <= observedAt`; otherwise `SYSTEM_ACTIVATE` only for lifecycle `SCHEDULED` when `start_at <= observedAt < end_at`. Completion therefore wins for a scheduled event whose entire window was missed. Each event appears at most once. Ordering is boundary ascending, then `SYSTEM_COMPLETE` before `SYSTEM_ACTIVATE`, then event UUID ascending under canonical UUID ordering. A persisted `REVISION_EXHAUSTED` SYSTEM receipt for the same event, revision and derived operation suppresses that exact identity from future selections; no other receipt suppresses a candidate. The selected snapshot supplies event id, aggregate revision and exact start/end boundary; every selected row is decoded and passed through the private candidate factory. Any row that the query selected but the closed decoder/factory rejects returns `CORRUPT` for the whole selection and processes no partial page.

The service processes the immutable candidate page sequentially in returned order. `COMPLETED` is exact `{observedAt,selected,applied,replayed,revisionConflicted,invalidTransition,revisionExhausted,missing,corrupt}`; all counts are non-negative integers and `selected = applied + replayed + revisionConflicted + invalidTransition + revisionExhausted + missing + corrupt`. A `REPLAY` counts only as `replayed`, regardless of its historical receipt outcome. A `NEW` receipt is classified exhaustively by the closed SYSTEM outcomes `APPLIED`, `REVISION_CONFLICT`, `INVALID_TRANSITION` or `REVISION_EXHAUSTED`; any other receipt outcome is corrupt. Selection corruption returns `CORRUPT_SELECTION` with the observed instant and no partial counters or writes. The service performs no unbounded retry, recursion, sleep or second page in the same invocation. A result count is derived from closed receipt/result types, not exception text. The service itself is not registered as a scheduler, timer, public controller or background executor in PCC-008C; PCC-008F alone may wire an invoker after later gates.

The candidate already proves due-ness against its retained selected snapshot. Its deterministic command UUID and canonical payload hash are derived without reading current state. The writer first performs a read-only global binding lookup: an existing exact SYSTEM EVENT-family binding returns its immutable receipt as `RECORDED/REPLAY` before any current lifecycle, revision or time evaluation; a mismatched binding is `CORRUPT` and leaks no competing identity. Only an unbound candidate re-reads the current event without locking. Absence returns `MISSING` with no write. If current revision still equals the candidate revision, event id, approved definition, complete snapshot and derived boundary must equal the retained snapshot or the result is `CORRUPT`; if revision changed, the immutable selected candidate remains valid input for a recorded CAS decision. No fresh clock is read.

The unbound writer acquires the command advisory lock, repeats the binding lookup, and applies the same replay/corruption rule so concurrent first use serializes. With no binding, it locks the event. Absence is `MISSING`; equal revision again requires exact equality with the retained snapshot and derived boundary, while a changed revision proceeds only to the normal CAS result. It evaluates transition rules at the original `candidate.observedAt` and atomically persists the existing EVENT-family SYSTEM receipt/audit plus any applied event snapshot. `recordedAt` for a SYSTEM receipt is defined as that authoritative decision instant, even if transaction commit occurs later. A revision mismatch records `REVISION_CONFLICT`; a concurrent valid winner can therefore apply once while another candidate selected with a different expected revision records its own result. A new scan of a still-eligible later revision obtains a distinct deterministic UUID.

PCC-008C requires no schema migration or new database privilege: it reuses immutable V36 event snapshots, global EVENT command bindings, SYSTEM receipt constraints, audit and the existing restricted event writer. Selection is read-only and lifecycle mutation still passes through the protected calendar event update. Tests must prove exact start/end boundaries, missed-window completion without activation, stable ordering and cap, concurrent cycles, replay after applied activation/completion and later lifecycle/time changes, revision race, revision exhaustion plus later-page progress, an early cycle whose query is blocked until after the boundary, candidate boundary non-forgeability, corrupt snapshot fail-closed behavior and absence of routes/timers/occurrence or notification effects. PCC-008C does not consult or mutate the reminder switch: lifecycle truth must advance independently of whether reminder delivery is disabled.

### PCC-008D exact durable occurrence claim contract

PCC-008D adds no wire or HTTP type. Its application boundary uses only closed types: `CalendarOccurrenceClaimResult PAGE|EMPTY|CORRUPT`, `CalendarOccurrenceTerminalReason LATE|SWITCH_DISABLED|SWITCH_EXPIRED|ENABLE_CUTOFF|EVENT_INELIGIBLE|DEFINITION_CHANGED|RESUME_CUTOFF|ATTEMPTS_EXHAUSTED|PERMANENT_FAILURE|UNKNOWN`, `CalendarOccurrenceFailureClass RETRYABLE_PRE_HANDOFF|PERMANENT_PRE_HANDOFF|UNKNOWN`, and `CalendarOccurrenceSettlementResult RETRY_SCHEDULED|DEAD|LOST_FENCE|MISSING|CORRUPT`. `CalendarOccurrenceBatchSize` accepts 1..50 and defaults to 50. `CalendarLeaseOwner` accepts only a non-zero UUID. The lease token is the immutable pair `{owner,attempt}` returned by a successful claim; callers cannot construct it with attempt outside 1..3. Domain/application code never branches on raw persisted strings.

`claim(owner,batchSize)` captures one authoritative UTC `observedAt`, truncated to whole seconds, before the database call or any lock wait. Persistence uses that same instant for due selection, lateness, switch effectivity and no-backfill cutoffs; it does not call database wall-clock functions. Candidate rows are `PENDING` with `scheduled_at <= observedAt` and `next_attempt_at <= observedAt`, plus `LEASED` with `lease_until <= observedAt`. Selection is ordered by `scheduled_at` ascending then canonical occurrence UUID ascending, capped before mutation to `batchSize`, and locked with `FOR UPDATE SKIP LOCKED`, so concurrent claimers receive disjoint rows without waiting for one another. The selected page is immutable. After every selected occurrence, singleton and event row needed by the page is locked and validated, the service captures a second authoritative whole-second `leaseGrantedAt`; every newly leased row in that page uses `lease_started_at = leaseGrantedAt` and `lease_until = leaseGrantedAt + 60 seconds`. Thus a query blocked longer than 60 seconds still evaluates eligibility only at the early `observedAt` but never returns an already-expired lease. Any selected row, referenced rule/event/switch snapshot or applied-resume audit that cannot be decoded through its closed translator aborts the whole transaction and returns `CORRUPT`; no partial lease or terminal settlement commits.

For each selected row, an expired lease already at attempt three first becomes `DEAD/ATTEMPTS_EXHAUSTED`; it is never reclassified or leased. Other terminal decisions precede leasing in this exact order: `scheduled_at < observedAt - 15 minutes` is `SKIPPED/LATE` (exact 15-minute lateness remains eligible); switch configured disabled; switch enablement expired; effective-enable cutoff; approved-definition mismatch; ineligible event lifecycle; latest-resume cutoff. Structurally invalid or closed `UNKNOWN` data is `CORRUPT` for the page, never `SKIPPED`. Switch effectivity is derived under the singleton lock at `observedAt`. An effective enablement skips when `scheduled_at <= switch.created_at`, making the latest successful enable command the durable no-backfill cutoff. The referenced current event is locked and must decode, retain the same approved definition revision and be `SCHEDULED|ACTIVE`. The authoritative latest resume is the immutable audited `APPLIED/RESUME` receipt with the greatest decoded `after.revision`, not the greatest timestamp; revisions are unique within an event. Its `recordedAt` is the durable resume cutoff and skips when `scheduled_at <= recorded_at`. Only after all checks does a row lease.

A lease transition increments attempts exactly once, changes `PENDING|expired LEASED -> LEASED`, installs the requested owner, sets the shared page `leaseGrantedAt` and its 60-second deadline, clears retry/terminal metadata and returns the occurrence plus `{owner,attempt,observedAt,leaseGrantedAt,leaseUntil}`. Attempts never exceed three. An expired third-attempt lease is settled `DEAD/ATTEMPTS_EXHAUSTED` during claim and cannot be leased again. A crash before settlement leaves `LEASED`; no cleanup clock mutates it, and a later claim re-evaluates every no-backfill guard before either leasing the next attempt or terminalizing it. `EMPTY` means exactly `selected=0`. `PAGE` means `selected>0` and reports exact non-negative `{observedAt,leaseGrantedAt,selected,leased,skipped,dead}` counters plus the leased records; a fully terminalized page is still `PAGE` with zero records. Always `selected = leased + skipped + dead` and `leased = records.size`. The service performs one page, no sleep, recursion or unbounded retry.

`settleFailure(occurrenceId,leaseToken,failureClass,settledAt)` is an internal transaction and accepts a whole-second authoritative instant captured before its database call. It locks the row and mutates only when state is `LEASED`, both owner and attempt equal the token, and `lease_started_at <= settledAt < lease_until`. Missing is `MISSING`; a different/absent/expired fence or a settlement instant before lease start is `LOST_FENCE` with no write. `UNKNOWN` is rejected as `CORRUPT` with no write rather than converted from exception text. `RETRYABLE_PRE_HANDOFF` on attempt one returns the row to `PENDING` with `next_attempt_at = settledAt + 30 seconds`; on attempt two it uses `settledAt + 2 minutes`; on attempt three it settles `DEAD/ATTEMPTS_EXHAUSTED`. `PERMANENT_PRE_HANDOFF` settles `DEAD/PERMANENT_FAILURE` at any attempt. All successful settlements clear owner, lease start and lease deadline and persist the closed failure class; the next successful lease clears prior failure and terminal metadata. PCC-008D has no generic `catch` that calls this method: only an explicitly proven failure before handoff may do so. Unclassified process/connection failure leaves the lease for expiry-based recovery.

The migration adds exact columns `next_attempt_at`, `lease_started_at`, `terminal_reason`, `terminal_at` and `last_failure_class`. Existing initial `PENDING` rows receive `next_attempt_at=scheduled_at`. State invariants are normative: initial `PENDING` has attempts 0, non-null next attempt and all lease/terminal/failure fields null; retry `PENDING` has attempts 1..2, non-null next attempt, `last_failure_class=RETRYABLE_PRE_HANDOFF` and no lease/terminal fields; `LEASED` has attempts 1..3, non-null owner/start/until with `until=start+60 seconds`, and all retry/terminal/failure fields null; `SKIPPED` has attempts 0..2, one skip-only terminal reason plus terminal instant and every lease/retry/failure field null; `DEAD` has attempts 1..3, reason `ATTEMPTS_EXHAUSTED|PERMANENT_FAILURE`, terminal instant, no lease/retry fields, and failure class respectively null-or-retryable or permanent; legacy/future `EMITTED` has attempts 1..3 and no lease/retry/terminal/failure fields. Every timestamp is whole-second.

The only PCC-008D transitions are initial/retry `PENDING -> LEASED` with attempts incremented; expired `LEASED` attempt 1..2 `-> LEASED` with attempts incremented and a replacement fence; `PENDING` or expired `LEASED` attempt 1..2 `-> SKIPPED` by the ordered guards; expired `LEASED` attempt 3 `-> DEAD/ATTEMPTS_EXHAUSTED`; valid fenced `LEASED` attempt 1..2 `-> PENDING` for retryable failure; valid fenced `LEASED` attempt 3 `-> DEAD/ATTEMPTS_EXHAUSTED`; and valid fenced `LEASED -> DEAD/PERMANENT_FAILURE`. Terminal rows never reopen, and PCC-008D permits no transition to `EMITTED`. Constraints plus an occurrence-update trigger reject every other state/metadata combination and transition.

Runtime keeps direct occurrence `UPDATE` revoked. Narrow `SECURITY DEFINER` mutation functions validate every closed argument, schema-qualify every relation/function, declare `SET search_path=pg_catalog,public,pg_temp`, revoke all execution from `PUBLIC` and runtime, then grant only the required signatures to runtime; migrator retains ownership. Owner+attempt+unexpired-lease predicates are repeated in the settlement update itself, not checked only in application memory. A `CORRUPT` result means closed decoding/relational inconsistency; database connectivity, timeout and transaction failures propagate after rollback and are never relabelled as corrupt business data. PCC-008E alone may replace the protected transition contract with the atomic stable-key notification insert plus `EMITTED` settlement. Until then there is no path to `EMITTED` and no notification side effect.

Adversarial tests must prove page cap/order, a fully terminalized non-empty page, exact due and 15-minute boundaries, switch disabled/expiry/re-enable cutoff, pause/cancel/complete and latest-resume-by-revision cutoff (including inverted recorded timestamps and exclusion of non-applied receipts), definition mismatch, two concurrent claimers, expired-lease takeover, stale-owner fencing, settlement immediately before/at/after expiry, first/second backoff, third-attempt death crossed with every higher-precedence guard, permanent failure, process crash followed by recovery, corruption rollback with no partial page, database lock crossing a due/lateness boundary while retaining the early captured instant, a lock wait longer than 60 seconds that still returns a fresh 60-second lease, privilege/invalid-metadata attacks against mutation functions, and absence of runner beans/routes/notifications. PCC-008D remains inactive; PCC-008F alone may wire an invoker after PCC-008E and all reviews pass.

### PCC-008E exact atomic in-app CAMPAIGN handoff contract

PCC-008E adds no wire or HTTP type. Its application boundary is the closed `CalendarOccurrenceHandoffResult EMITTED|REPLAYED|SKIPPED|LOST_FENCE|MISSING|CORRUPT`. `EMITTED` and `REPLAYED` retain the validated notification alert id; `SKIPPED` retains one existing closed skip-only `CalendarOccurrenceTerminalReason`. The handoff accepts only the immutable `CalendarOccurrenceLease` returned by PCC-008D; callers cannot supply occurrence identity, owner or attempt separately. Domain/application code never branches on raw persisted or notification strings.

`handoff(lease)` starts one transaction by locking the occurrence row, then reads immutable handoff evidence while that lock is held. Exact evidence binds occurrence id, lease owner, attempt, notification delivery id, alert id and emitted instant. When the occurrence is `EMITTED`, evidence plus the referenced notification alert/source event must decode and match the complete normative identity below. The same owner+attempt returns `REPLAYED` before evaluating the current switch, event, definition, resume or clock; any different fence is `LOST_FENCE` without exposing the alert id, while missing/malformed/inconsistent evidence is `CORRUPT`. An `EMITTED` occurrence without evidence, evidence for a non-`EMITTED` occurrence or notification evidence without the atomic handoff row is corrupt and is never repaired by replay. A concurrent caller that initially observed no evidence must re-read occurrence plus evidence after acquiring the occurrence lock; it cannot classify from a pre-lock observation.

For a first handoff, persistence locks in this order: occurrence, reminder-switch singleton and current event; it reads the trigger-protected immutable approved definition/rule and applied RESUME receipts needed to derive the latest revision; then it takes the existing notification delivery advisory lock and a notification episode advisory lock derived from the complete normative episode identity. Runtime has no update privilege on the immutable definition/rule/receipt relations, so it does not widen privileges merely to request a row lock. It decodes every value through its closed translator and proves that no delivery or episode exists before mutation. Only after every mutable-row/advisory lock, possible wait and validation does it capture a fresh authoritative UTC `handoffAt`, truncated to whole seconds. The lease is actionable only when the occurrence is still `LEASED`, owner and attempt equal the token, `lease_started_at <= handoffAt < lease_until`, and the immutable occurrence fields equal the retained lease. A missing row is `MISSING`; state/token/time mismatch is `LOST_FENCE`; structural or identity mismatch is `CORRUPT`. The typed ingestion operation reacquires only those already-held transaction-scoped advisory locks and performs no new blocking lookup; a lock wait therefore cannot use an early timestamp to extend a lease.

With a valid fence, all PCC-008D no-backfill guards are re-evaluated at `handoffAt` in the same precedence, except attempt exhaustion which belongs to claim: more than 15 minutes late, configured switch disabled, enabled switch expired, scheduled instant at/before current enablement instant, approved definition mismatch, event lifecycle outside `SCHEDULED|ACTIVE`, and scheduled instant at/before the latest applied RESUME `recordedAt` selected by greatest decoded `after.revision`. The event row remains locked through commit, so pause/cancel/complete cannot cross the decision. A guard commits `LEASED -> SKIPPED` with the exact existing reason and `terminal_at=handoffAt`, clears the lease, creates no notification/evidence and returns `SKIPPED`. Unknown/corrupt state rolls back and returns `CORRUPT`; database timeout/connectivity/transaction failures propagate and are never translated as business corruption.

The normative notification identity is fixed and derived only from the durable occurrence: `delivery_id = occurrence.id`; source type `SYSTEM_CAMPAIGN`; source id is the canonical lowercase occurrence UUID; category `CAMPAIGN`; severity `INFO`; condition code `CALENDAR_REMINDER_DUE`; episode key is the same canonical occurrence UUID. Fingerprint and event hash use the existing `notification-v1` and `notification-event-v1` length-framed functions over those exact fields. The producer never accepts title, body, recipient, address, severity, category, source id or episode key from a caller. `campaignReference` remains merchant metadata and is not part of delivery identity or authority. The existing notification uniqueness `(source_type,source_id,fingerprint)` and delivery UUID make a second alert impossible.

Notification ingestion exposes a closed disposition `CREATED|DELIVERY_REPLAY|EPISODE_REUSED|DELIVERY_CONFLICT|UNKNOWN` rather than treating every `Recorded(alert)` as equivalent. All notification producers acquire delivery advisory then episode advisory locks in that order before checking/inserting, and the disposition is decided under both locks. Normal notification ingestion may continue to append a new delivery to an existing episode as `EPISODE_REUSED`; PCC-008E is stricter and accepts only `CREATED`. Because handoff already owns both locks and proved absence, any other disposition or a returned alert not OPEN with exact identity/revision zero is `CORRUPT` and rolls back the transaction. This typed witness, not `ON CONFLICT DO NOTHING` or an unlocked precheck, proves that the alert was created by this handoff.

The notification source event, immutable `calendar_occurrence_handoffs` evidence and occurrence `LEASED -> EMITTED` transition commit in that one transaction. Any conflict, closed-type mismatch, insert failure or failed fenced update rolls the whole transaction back, including the alert. The occurrence clears lease/retry/terminal/failure fields and retains attempts 1..3. No pre-handoff failure settlement is manufactured after notification ingestion begins; an unclassified rollback leaves the original lease for expiry recovery.

Migration PCC-008E adds immutable `calendar_occurrence_handoffs(occurrence_id,lease_owner,attempt,delivery_id,alert_id,emitted_at)` with non-zero UUIDs, attempts 1..3, whole-second emitted time, `delivery_id=occurrence_id`, foreign keys to occurrence, notification delivery and alert, and uniqueness for delivery/alert linkage. Deferred consistency triggers require exact notification source/episode fields and `EMITTED` occurrence state in both directions at commit. The V38 occurrence shape is extended forward-only so `SKIPPED` accepts attempts 0..3, and the closed persistence decoder is changed to the same range. Claim precedence remains unchanged: an already expired third lease becomes `DEAD/ATTEMPTS_EXHAUSTED`; only a still-valid third lease may become `SKIPPED` when a guard newly fails at handoff. The PCC-008D occurrence protection is replaced, not bypassed: it additionally permits only valid fenced unexpired `LEASED -> EMITTED` with exact handoff evidence and valid fenced unexpired `LEASED -> SKIPPED` for a newly failed no-backfill guard. Direct occurrence update and handoff-table DML remain revoked from runtime. Any narrow `SECURITY DEFINER` writer schema-qualifies relations/functions, uses `SET search_path=pg_catalog,public,pg_temp`, validates closed arguments, repeats owner+attempt+unexpired predicates in the final update, is revoked from `PUBLIC`, and grants only its exact signature to runtime.

CAMPAIGN remains excluded from operational email consent. The handoff must create zero `notification_email_outbox` rows even when email readiness is READY and users have operational opt-in; it calls no SMTP or other external transport. It registers no bean that runs automatically, no scheduler, timer, thread, route, capability/readiness promotion or switch mutation. PCC-008F alone may compose claim plus handoff and activate an invoker after its separate GO.

## Delivery and failure

In-app notification persistence commits before optional email delivery. Email uses an outbox and retry policy; it cannot change alert lifecycle. Report freshness is explicit. BlackStore commercial reporting produces `NOT_AVAILABLE`; stock freshness may be `UNAVAILABLE` or `STALE`, never zero. Loyalty uncertainty blocks a second loyalty effect until reconciliation but never blocks an independently authoritative refund or return.

The optional email projection is a separate PCC-003B gate. Until recipient selection, explicit opt-in, verified address policy, versioned template, backfill and retry semantics pass review, readiness is `UNCONFIGURED`, no notification email outbox is enqueued and no SMTP scheduler or transport is active. Identity recovery/verification outboxes are not reused.

Calendar reminder delivery does not reuse or widen PCC-003B. V1 produces only an authenticated same-origin in-app CAMPAIGN alert. It accepts no address and creates no email intent because CAMPAIGN remains excluded from operational-email consent. The reminder switch defaults to DISABLED, and no scheduler, thread, timer or transport is wired in PCC-007.

PCC-003B freezes those contracts as follows. Preferences are owned by the authenticated USER and bound to its current positive `email_version` plus SHA-256 digest proven by `identity_email_verification_evidence` for realm USER. ADMIN and OPERATOR may opt themselves in; CUSTOMER and third-party administration are excluded. Preference operations are closed `ENABLE|DISABLE`, revisioned, idempotent, same-origin JSON/CSRF commands. ENABLE requires non-empty subsets of operational categories `STOCK|ORDER|PAYMENT|RETURN|INTEGRATION` and severities `WARNING|CRITICAL`; DISABLE carries no filters. A changed email, lost role, inactive user or opt-out never reactivates automatically.

Email readiness is closed `UNCONFIGURED|UNAVAILABLE|READY|UNKNOWN` and separate from delivery state. Production PCC-003B is wired `UNCONFIGURED`: no scheduler, credentials, SMTP transport, network call or historical backlog. Tests may inject an explicit READY double. When READY, an eligible intent is inserted in the same database transaction that first creates its alert; finding an existing episode never projects again. `UNIQUE(alert_id,user_id)` prevents resends across resubscription, address or template changes. The queue stores only user id and email version/digest binding, not plaintext destination; the address is resolved and revalidated immediately before handoff.

Delivery state is closed `PENDING|LEASED|RETRY|SENT|UNCERTAIN|DEAD|CANCELLED|UNKNOWN`. PENDING/RETRY may lease or cancel; LEASED may settle SENT/RETRY/UNCERTAIN/DEAD/CANCELLED; terminal and UNKNOWN states never reopen. TTL is 24 hours, lease is 60 seconds and the maximum is five attempts. Backoff is 30 seconds, 2 minutes, 10 minutes and 30 minutes plus injectable ±20% jitter. Retry is allowed only for a proven failure before DATA. A lease lost after durable handoff start, or an unclassified exception, becomes UNCERTAIN with no automatic retry or manual resend in V1. Preference, role, active state, email binding, verification, TTL and lease ownership are revalidated immediately before marking handoff started. Transport failure never mutates an alert.

Template is the closed `OPERATIONAL_ALERT_V1`. Renderer output is generic and contains only a same-origin authenticated notification-center link; source id, order, amount, customer data, actor, lifecycle reason and producer-provided text are forbidden. Preference receipts/audit and outbox/delivery evidence are append-only; identity outboxes remain untouched.
