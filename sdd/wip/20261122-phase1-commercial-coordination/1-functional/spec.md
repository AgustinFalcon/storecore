# Functional specification — Phase 1 commercial coordination

## Objective

Complete the integral StoreCore Phase 1 with operator-facing coordination that is useful without external homologation: one notification center, a configurable commercial calendar, consolidated StoreCore/BlackStore visibility and a promotional loyalty balance. The system must never describe fictitious points as money or cryptocurrency.

## Actors

- `ADMIN`: configures rules, acknowledges, resolves and reopens alerts, manages campaigns and performs audited loyalty adjustments.
- `OPERATOR`: reads operational alerts, calendar and reports. It is read-only for notification and calendar lifecycle commands.
- `CUSTOMER`: reads its own loyalty balance and immutable movement history, and may request or cancel a redemption reservation for its own checkout under the active policy.
- `SYSTEM`: records deterministic events from authoritative StoreCore facts and, only when enabled, accepted BlackStore receipts.

## Slice A — notification center

- PCC-R01: expose one paginated inbox for stock, order, payment, return, integration and campaign alerts.
- PCC-R02: severity, category, lifecycle and source are closed types. Unknown wire values render as neutral unknown and cannot trigger actions.
- PCC-R03: acknowledge, resolve and reopen are explicit idempotent commands with actor, timestamp, reason and revision.
- PCC-R04: duplicate source events converge on one alert fingerprint; a replay cannot create a second alert.
- PCC-R05: email is an optional delivery projection. Failed or disabled SMTP never loses the in-app alert.
- PCC-R05A: Slice A freezes the vocabularies as severity `INFO`, `WARNING`, `CRITICAL`, `UNKNOWN`; category `STOCK`, `ORDER`, `PAYMENT`, `RETURN`, `INTEGRATION`, `CAMPAIGN`, `UNKNOWN`; lifecycle `OPEN`, `ACKNOWLEDGED`, `RESOLVED`, `UNKNOWN`; source type `STORECORE_FACT`, `BLACKSTORE_STOCK_RECEIPT`, `SYSTEM_CAMPAIGN`, `UNKNOWN`.
- PCC-R05B: the only valid lifecycle graph is acknowledge `OPEN -> ACKNOWLEDGED`, resolve `OPEN|ACKNOWLEDGED -> RESOLVED`, and reopen `RESOLVED -> OPEN`. Self-transitions, commands from `UNKNOWN` and every other jump fail closed. A replay is recognized only by its original command receipt, never because the aggregate already has the requested destination state.
- PCC-R05C: `source_id` is the stable authoritative identifier supplied by the typed producer, not a URL, localized label or delivery UUID. One alert episode is identified by `(source_type, source_id, fingerprint)`. The V1 fingerprint hashes the length-framed UTF-8 tuple `notification-v1`, category, stable condition code and producer-owned episode key. Delivery time, title, localized body, severity and personal data are excluded. A retry reuses the same episode key; a genuine recurrence must provide a new stable episode key. Duplicate events never reopen a resolved alert.
- PCC-R05D: ADMIN and OPERATOR can read the paginated inbox and current detail. Only ADMIN can acknowledge, resolve or reopen. Receipt recovery is private to the ADMIN actor that created the command; other actors receive the same not-found response as an absent receipt.
- PCC-R05E: Slice A delivery is split into HTTP/read delivery and a separately reviewed optional email projection. HTTP completion does not imply email consent, SMTP readiness or transport activation. Email remains disabled until recipient, consent, template and historical-backfill policy are approved.
- PCC-R05F: email opt-in is self-service only for an active USER with current ADMIN or OPERATOR role and verified current email identity. The request never accepts a recipient, user identifier, sender or address. Enabling requires explicit selection of at least one operational category (`STOCK`, `ORDER`, `PAYMENT`, `RETURN`, `INTEGRATION`) and at least one severity (`WARNING`, `CRITICAL`); `CAMPAIGN`, `INFO` and `UNKNOWN` are excluded in V1. Disabling remains available to the owner even when the prior address is no longer verified.
- PCC-R05G: one user receives at most one email intent per alert episode. Opt-in applies only to alerts first created after the consent and after a future explicit delivery enablement; no historical backfill occurs. Duplicate source deliveries, lifecycle transitions, template changes, address changes and resubscription never create another intent for the same `(alert,user)`.
- PCC-R05H: `OPERATIONAL_ALERT_V1` is the only template. It contains a generic subject/body and an authenticated same-origin link; it excludes source identifiers, orders, amounts, customer data, actor, reason and producer text. Opt-out, email change, role loss or user deactivation cancels work that has not begun handoff. Email failure never changes alert lifecycle.

## Slice B — commercial calendar

- PCC-R06: merchants create draft events with timezone, start/end, audience, campaign reference and optional reminder rules.
- PCC-R07: lifecycle is `DRAFT`, `SCHEDULED`, `ACTIVE`, `PAUSED`, `COMPLETED`, `CANCELLED`, `UNKNOWN`; transitions are closed commands and invalid jumps fail closed.
- PCC-R08: scheduling requires preflight, explicit approval, bounded window and revision compare-and-set. This first slice is agenda/reminders only: it never changes price, offer, stock, checkout or customer eligibility. Pause stops future reminders without deleting history.
- PCC-R09: no named holiday or promotion is hardcoded. Black Friday is ordinary merchant data.
- PCC-R10: calendar UI provides month/list views, filters, empty/error/loading states and accessible keyboard navigation.
- PCC-R10A: ADMIN creates and edits drafts, requests preflight, explicitly schedules, pauses, resumes and cancels. OPERATOR reads events only. SYSTEM may activate and complete an already approved event from the authoritative clock; it cannot edit definitions or approve a schedule. CUSTOMER has no calendar route. Every command and replay revalidates the live USER session and role.
- PCC-R10B: the only lifecycle graph is create `-> DRAFT`; schedule `DRAFT -> SCHEDULED`; pause `SCHEDULED|ACTIVE -> PAUSED`; resume `PAUSED -> SCHEDULED` before the start or `PAUSED -> ACTIVE` inside the window; cancel `DRAFT|SCHEDULED|ACTIVE|PAUSED -> CANCELLED`; SYSTEM activate `SCHEDULED -> ACTIVE` inside the window; and SYSTEM complete `SCHEDULED|ACTIVE|PAUSED -> COMPLETED` at or after the end. Edit changes a definition while lifecycle remains DRAFT; it is not a lifecycle transition. A draft never advances by time. Lifecycle self-transitions, terminal-state commands, commands from `UNKNOWN` and every other jump fail closed. Recovery after downtime applies the same clock guards and may complete a window without first emitting an activation.
- PCC-R10C: V1 audience is closed to `INTERNAL_ALL`, `UNKNOWN`. It means the same operational calendar/reminder is visible to active ADMIN and OPERATOR USER principals; it never accepts a user id, CUSTOMER, role subset, free-form recipient or email address. Role-specific audiences are deferred until a separate recipient-ACL contract exists. Campaign reference is optional merchant metadata, not authority to activate a price or offer.
- PCC-R10D: V1 accepts whole-second local date-times with an IANA timezone and explicit numeric UTC offset. A nonexistent DST local time is rejected. For an overlapping local time, the supplied offset selects one of the two valid instants; any other offset is rejected. The approved start/end instants, timezone and chosen offsets are retained. Windows are `[start,end)`, start must precede end, scheduling requires start at least five minutes in the future, start is at most 366 days ahead and duration is at most 90 days.
- PCC-R10E: preflight is an ADMIN operation that returns a typed result bound to event id, current revision, canonical definition hash, server time and a ten-minute expiry. Schedule must reference that exact preflight and explicitly approve it. A definition edit, revision change, expiry or blocking issue invalidates approval. Schedule revalidates the snapshot and clock atomically; a stale preflight never schedules a newer definition.
- PCC-R10F: V1 reminder channel is only same-origin in-app `CAMPAIGN`; it never sends email or calls an external provider. A draft may contain zero to five unique offsets, each from five minutes through 30 days before start. One occurrence is identified by event, approved definition revision, rule and scheduled instant. Lifecycle revision changes caused by pause, resume, activation or completion do not re-key the occurrence; the worker instead locks and revalidates current lifecycle plus the unchanged approved definition revision. Paused/cancelled/completed events and a disabled kill switch cannot create an effect. Occurrences more than 15 minutes late are skipped; resume never backfills missed reminders. Retry preserves the same occurrence identity.
- PCC-R10G: the reminder kill switch is closed `DISABLED`, `ENABLED`, `UNKNOWN`, defaults to `DISABLED`, and its eventual mutation is ADMIN-only, revisioned, idempotent and audited. Disabling prevents new claims; an already claimed occurrence revalidates switch, event lifecycle and revision immediately before the in-app effect and otherwise becomes skipped. PCC-007B exposes only the ADMIN diagnostic read with closed runner readiness `UNAVAILABLE`; it registers no switch-command route and grants no mutation privilege. PCC-008 owns the command, receipt, temporary metadata required by `sdd/PATTERNS.md` and activation gate; until that reviewed contract lands, `/reminder-switch/commands` is unmapped and returns 404.
- PCC-R10H: titles are 1..120 Unicode code points, descriptions 0..1,000, optional campaign references 1..64 uppercase ASCII characters plus digits, `_`, `-` and `.`, and transition reasons 1..500 code points under the shared trim rule. List queries select strict overlaps (`start < to` and `end > from`), are paginated, bounded to a maximum 366-day window and never return audit actor/reason to OPERATOR. Audit is append-only, ADMIN-only, paginated and stably ordered by recorded instant then command id; an absent event is 404 while an existing event with no audit entries is an empty 200 page.
- PCC-R10I: month and list are two views of the same bounded, paginated query. Month never claims that an unrequested page is an empty day or a complete count; it presents the loaded page projected by date, the absolute result count, page position and persistent previous/next controls. Loading, refreshing, stale, empty, denied, invalid, unavailable and corrupt-data states are distinct closed presentation states. Edited-but-unapplied filters are not announced as server results.
- PCC-R10J: the calendar URL owns a closed view mode, an ISO `YYYY-MM` visible month, an explicit IANA display zone, lifecycle/audience filters, page and size. Repeated, unknown or malformed parameters fail closed. Month boundaries are resolved as `[local month start,next local month start)` in that zone rather than by adding 24-hour days. The selected display zone is always visible; event detail preserves and displays each approved event zone and offset. The UI never silently substitutes the browser zone or normalizes a DST gap/overlap.
- PCC-R10K: ADMIN has separate create/edit, review/preflight, explicit schedule confirmation, lifecycle confirmation, audit and reminder-diagnostic surfaces. OPERATOR has month/list/detail only and never requests private audit, receipts, preflight or switch data. CUSTOMER has no route. `SYSTEM_*` operations may appear as read-only audit history but never as UI actions.
- PCC-R10L: every uncertain create, edit, preflight or lifecycle request is journaled with its exact UUID, payload, USER actor and authentication epoch before POST. The UI blocks a second mutation until exact replay or private receipt recovery resolves the first; actor, role or epoch changes clear data and invalidate late responses. CREATE recovers by command lookup; event commands recover by event/command lookup; PREFLIGHT recovers by replaying the exact POST because it has no receipt GET. A new preflight after expiry is a new explicit intent and UUID.
- PCC-R10M: preflight review shows the exact event, aggregate revision, definition revision/hash, approved times/zones/offsets, audience and reminder rules plus server expiry. Scheduling is disabled when the snapshot is blocking, expired, corrupt or no longer matches the refreshed event. Browser time may explain expiry but is never authority for applying a transition.
- PCC-R10N: PCC-008A may configure reminder rules as draft data and show ADMIN diagnostics, but readiness `UNAVAILABLE` is rendered as “recordatorios no disponibles en esta versión”. It exposes no ENABLE action and does not claim delivery. Switch mutation, durable no-backfill semantics, worker fencing/handoff and activation are separate reviewed cuts PCC-008B..F.
- PCC-R10O: PCC-008B closes the reminder-switch command without activating a runner. The only operations are `ENABLE`, `DISABLE`, `UNKNOWN`; ADMIN is the only caller and OPERATOR/CUSTOMER/SYSTEM have no mutation or receipt access. Both operations use aggregate-revision compare-and-set, an exact non-zero UUID idempotency key and the same live USER actor/session checks as calendar commands. A new command that requests the already effective state is an invalid transition; an exact replay returns its historical receipt only to the original actor.
- PCC-R10P: every new switch command carries exact temporary governance metadata: `owner` (1..160 trimmed code points), `reason` (1..500), `removalTicket` (1..100), fixed affected action `EMIT_IN_APP_CAMPAIGN_REMINDER`, and a whole-second UTC `expiresAt` strictly more than five minutes and at most seven days after the authoritative server instant. `createdAt` is server-owned. The revision-zero bootstrap `DISABLED` row is the sole metadata-free state. A successful later command always replaces the complete metadata set and preserves the previous set in immutable audit and receipt snapshots. Exact replay is resolved from its immutable binding and receipt before re-evaluating relative expiry, current revision, transition or capability, so later clock/configuration changes cannot rewrite historical outcome.
- PCC-R10Q: `ENABLE` is accepted only while the typed `COMMERCIAL_CALENDAR` capability is already `ACTIVE`, the exact reminder action is allowlisted and no effective capability kill denies it. The command never promotes capability, readiness or configuration. `DISABLE` is a safety operation and remains available to an authenticated ADMIN even when capability is disabled, paused, errored, missing or killed. It never starts, stops or claims a runner in PCC-008B.
- PCC-R10R: enabled state is temporary. Once its `expiresAt` is reached, effective state is `DISABLED` even if the last configured state was `ENABLED`; reads and future workers fail closed without relying on a cleanup timer. A new `ENABLE` may replace an expired enablement through revision CAS. Expiry of a `DISABLED` command never re-enables anything. Diagnostic and audit responses distinguish configured state from closed effectivity `DISABLED`, `EFFECTIVE`, `EXPIRED`, `UNKNOWN`, while readiness remains `UNAVAILABLE` throughout PCC-008B.
- PCC-R10S: malformed/unknown/additional fields, invalid metadata, unauthorized requests and absent receipts create no receipt. Well-formed authorized commands against the singleton record commit one immutable receipt for `APPLIED`, `REVISION_CONFLICT`, `INVALID_TRANSITION`, `CAPABILITY_NOT_ACTIVE` or `REVISION_EXHAUSTED`. Command UUID identity is global across event, preflight and reminder-switch families; reuse with a different family, actor, operation, revision or canonical payload is an idempotency conflict.
- PCC-R10T: PCC-008C advances only already-approved calendar lifecycles through an internal bounded SYSTEM cycle. One authoritative whole-second cycle instant is captured before candidate selection or any blocking operation. At that instant, `SCHEDULED` is eligible for activation only in `[start,end)`, while `SCHEDULED`, `ACTIVE` or `PAUSED` is eligible for completion at or after `end`; completion takes precedence, so a missed scheduled window completes without a synthetic activation. Draft, terminal, unknown and not-yet-due events are never candidates.
- PCC-R10U: a cycle selects at most 100 candidates in stable boundary/operation/event order and applies each with deterministic SYSTEM command identity plus aggregate revision CAS. Waiting for a query or lock cannot turn an early cycle into a valid transition: the captured cycle instant remains the selection and decision instant, an early cycle selects nothing and records no binding or receipt, and a later due cycle remains able to use the deterministic command. Concurrent cycles may replay or record a revision conflict but cannot apply a lifecycle transition twice. A revision-exhausted identity is audited once and omitted from later candidate pages so it cannot starve subsequent events. PCC-008C adds no public route, timer, scheduled/background activation, occurrence claim, notification, email or external effect.
- PCC-R10V: PCC-008D may durably claim an already-created reminder occurrence but still creates no notification. One whole-second claim instant is captured before persistence. A claim page contains at most 50 due `PENDING` occurrences whose retry time has arrived or expired `LEASED` occurrences, in scheduled-instant then occurrence-id order. Every lease is exactly 60 seconds and is fenced by the non-zero owner UUID plus the incremented attempt number. A stale or crashed owner can never settle a newer lease. There are at most three lease attempts; expiration of the third lease becomes `DEAD` rather than reopening.
- PCC-R10W: no-backfill is durable rather than inferred from the current UI. An occurrence is `SKIPPED` when it is more than 15 minutes late, the switch is disabled or expired, its scheduled instant is at or before the current enablement instant, its approved definition no longer matches, the event is not currently `SCHEDULED|ACTIVE`, or its scheduled instant is at or before the latest applied resume instant. A corrupt/unknown switch, event, receipt or occurrence is not a skip: it fails the whole claim page closed with no partial writes. Thus re-enable and resume never release work that became due while delivery was suppressed. A proven transient failure before handoff retries after 30 seconds on attempt one and two minutes on attempt two; a proven permanent pre-handoff failure or exhausted third attempt becomes `DEAD`. Unclassified failure does not manufacture a retry settlement: the durable lease expires and recovery re-reads authoritative state. PCC-008D registers no route, timer, scheduler, notification insert, email or external call.
- PCC-R10X: PCC-008E is the sole handoff from a valid fenced occurrence lease to an in-app alert. Immediately before the effect it serializes on the occurrence, switch and current event, captures a fresh whole-second server instant, rechecks the unexpired owner+attempt fence and every no-backfill guard, then either commits one `SYSTEM_CAMPAIGN/CAMPAIGN/INFO` notification together with occurrence `EMITTED`, or commits only the exact `SKIPPED` reason. The notification delivery, source and episode identities are the occurrence UUID, so retry after a lost response replays the immutable handoff evidence and cannot create a second alert. A stale/expired fence, absent occurrence or corrupt/inconsistent evidence creates no effect. This cut creates no email intent, transport call, public route, timer, scheduler or automatic worker activation.
- PCC-R10Y: PCC-008F activates one bounded local calendar invocation only when exact property `storecore.calendar.runner-enabled=true`; absent, false and every other value keep the invoker absent and readiness `UNAVAILABLE`. An active invocation reports readiness `READY`, meaning only that the reviewed local lifecycle, claim and handoff composition is wired; it never means the reminder switch is effective, the capability is active, the last tick succeeded or an external service is healthy. Each non-overlapping tick runs at most one 100-event SYSTEM lifecycle page, then one 50-occurrence claim page, then hands those leases off sequentially in stable claim order. It performs no second page, recursion, sleep, inline retry, email or external call. Lifecycle corruption aborts before claim; claim corruption aborts before handoff; handoff corruption or an infrastructure exception aborts the remaining page and leaves every uncommitted lease to fenced expiry recovery. Concurrent JVMs remain safe through the existing database identities, leases and fencing. The default remains inactive, no public trigger route is added, and enabling or disabling the audited reminder switch never creates, removes or changes runner readiness.

## Slice C — cross-channel reporting

- PCC-R11: expose authoritative StoreCore facts and a separate BlackStore integration-status/freshness panel. Do not infer BlackStore sales, payments or returns from stock saga receipts.
- PCC-R12: report periods use merchant timezone and immutable inclusive/exclusive boundaries shared by sales, payments, stock movements and returns.
- PCC-R13: the existing BlackStore contract contributes only its declared stock/version/availability fields. Monetary and commercial aggregates remain `NOT_AVAILABLE` until a separate read-only commercial-facts contract defines authority, event identity, corrections, reversals, retention, deduplication and version migration and passes its own SDD review.
- PCC-R14: StoreCore reports offer totals, best sellers, low stock, payment disposition and return disposition with CSV export protected against formula injection. Channel mix is shown only for authoritative sources; absent BlackStore facts are unavailable, never zero.
- PCC-R15: every card links to its filtered operational surface and preserves the exact report period.

## Slice D — loyalty ledger

- PCC-R16: loyalty is an internal promotional ledger denominated in integer `POINT`; it is not legal tender, cryptocurrency, withdrawable money or a customer deposit. Policy V1 grants 1 point per complete ARS 1,000 of eligible paid merchandise, rounding down, after authoritative payment approval. Shipping, taxes, outlet items and gift/loyalty value are ineligible.
- PCC-R17: movements are immutable `EARN`, `REDEEM`, `EXPIRE`, `REVERSAL`, `MANUAL_ADJUSTMENT`, `UNKNOWN` entries with source identity, actor and idempotency key.
- PCC-R18: balance is derived from accepted ledger entries. Negative balances, unsafe integer overflow and duplicate source credits fail closed.
- PCC-R19: Policy V1 converts 1 point to ARS 1 discount and caps redemption at the lesser of available points, 10% of eligible merchandise and 10,000 points per order, rounded down. It does not stack with manual or campaign discounts. The authenticated CUSTOMER explicitly selects points at checkout; quote, reserve and cancellation are customer commands. A quote reservation expires after 15 minutes. When a payment attempt is created it atomically becomes `PAYMENT_PENDING` and no longer expires by wall clock; it commits on authoritative approval and releases only on authoritative cancellation, rejection or failed order creation. Unknown provider outcome stays held for reconciliation, so a late approval never duplicates the benefit or creates a negative balance.
- PCC-R19A: `available = accepted credits - committed debits - active reservations - expired credits`. Reserve, commit, release and expiry serialize per customer ledger. Two reservations that jointly exceed available points cannot both succeed.
- PCC-R19B: earning entries expire 365 days after acceptance, oldest eligible points are consumed first, and expiry cannot consume an active reservation.
- PCC-R19C: returns use cumulative arithmetic per original order. `targetEarnReversal = floor(originalEarned * cumulativeEligibleReturned / originalEligibleBase)`, except a 100% return targets exactly all original earned points; each return records only the delta from prior reversals. The same cumulative-target/delta rule restores redeemed points and never exceeds the original redemption. If earned points were already spent, the return still completes and the uncovered amount becomes non-spendable `RECOVERY_PENDING`; balances never become negative and future earnings settle recovery first.
- PCC-R20: customer sees balance, expiry and history; administrator sees audited adjustment and reconciliation views. UI never prints an unknown raw state.

## Acceptance

1. Each slice demonstrates populated desktop and mobile states with deterministic synthetic fixtures.
2. All state/role/source/payment/transition vocabularies are closed domain types with one boundary translator and `Unknown`.
3. PostgreSQL tests prove migrations, idempotency, CAS/concurrency, immutable audit and tenant/realm ownership.
4. Browser tests cover success, empty, loading, error, stale data, permission denial and recovery.
5. StoreCore remains fully usable when BlackStore, SMTP and external providers are disabled.
6. No secret, live credential, personal identity or claim of external homologation is committed.
7. Numeric examples prove Policy V1: ARS 25,999 eligible earns 25 points; 800 available points on ARS 5,000 eligible can redeem 500; two concurrent reservations for 600 against 1,000 available yield one success and one insufficient-balance result. Two partial returns that together reach 100% reverse exactly all original earned points. A provider approval after the quote TTL still commits because the reservation was promoted to `PAYMENT_PENDING` before leaving checkout.

## Non-goals

- No live activation of BlackStore, SMTP, Mercado Pago, Mercado Libre, ARCA or Correo Argentino.
- No autonomous repricing, competitor scraping or hardcoded commercial campaign.
- No transferable token, cash withdrawal, peer-to-peer balance or crypto representation.
- No destructive rewrite of historic orders, payments, stock, returns or POS receipts.
- No BlackStore monetary aggregation until the separate commercial-facts contract is approved and implemented.
