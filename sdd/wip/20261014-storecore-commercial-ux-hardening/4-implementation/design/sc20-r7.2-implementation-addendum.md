# SC-SURF-20 R7.2 — addendum de implementación

Estado: `REVIEW_REQUIRED`. Este addendum corrige contradicciones descubiertas al
comparar el manifiesto histórico, el diseño Stitch R7/R7.1 y el runtime exacto
SC19 `8255d81480ce2e376e69546598c5c34c73f7962f`. No habilita implementación
hasta obtener los dos gates coordinados sin P1/P2.

## Precedencia

Para SC20 prevalecen, en este orden:

1. el snapshot SC19 persistido y su ledger de posventa;
2. este addendum;
3. el ledger general y el brief R6.3, únicamente donde no contradigan 1 o 2;
4. Stitch como referencia de composición, nunca como fuente de hechos.

El runtime no se adapta a una captura. La captura representa el contrato aprobado.

## Decisiones cerradas

### Una sola fuente de pedidos

- La cola operativa se proyecta desde `DemoSnapshot.orders`, `actors` y
  `aftercare`. No se crea una segunda colección de pedidos.
- V8 agrega de forma aditiva los registros canónicos ausentes y preserva byte a
  byte los pedidos legacy `DEMO-*`, que siguen disponibles para sus escenarios
  pero no pertenecen a la cola SC20.
- La pertenencia a la cola se resuelve mediante un objeto de alcance canónico con
  los doce IDs `ORD-1007` y `ORD-1012..ORD-1022`; no se infiere por prefijo en la
  vista y no se copian los datos del pedido.
- La migración es idempotente: un ID existente sólo se acepta si sus hechos
  inmutables coinciden; nunca se sobrescribe silenciosamente.

### Fixture y migración V8 exactos

- V8 agrega los actores de los once pedidos ausentes con `id=buyer-{orderId en
  minúsculas}`, email/nombre del ledger, teléfono vacío, carrito/favoritos vacíos
  y cuenta activa. Una colisión de ID o email con otra identidad rechaza toda la
  migración; no fusiona personas.
- Las líneas conservan `sku`, cantidad e importe histórico. En el modelo legacy
  de dos presentaciones, `kit-completo`, `bare-tool`, `standard` y
  `outlet-unit-01` se traducen a `DemoProductVariant.Standard`; su identificador
  histórico se serializa aparte como `DemoHistoricalVariant` cerrado (`Kit`,
  `BareTool`, `Standard`, `OutletUnit01`, `Unknown`) en la línea V8. No se agrega
  un campo al snapshot rico `CatalogOrderLineFacts` ni se habilita una
  presentación actual para comprar.
- Si falta `LMP-044`, V8 agrega el producto archivado mínimo necesario para
  validar su venta histórica. Si falta `VLD-043`, agrega una unidad Outlet no
  vendible. Cualquier colisión de SKU con producto incompatible aborta V8.
- V8 primero valida el invariante V7 existente. Luego agrega `ORD-1012` y aumenta
  en una unidad `DEMO-001.reserved`, sin cambiar `onHand`; finalmente vuelve a
  calcular el agregado desde **todos** los pedidos con pago Pending, incluidos
  pedidos previos del usuario. Las referencias históricas de ORD-1013/1017/1022
  no consumen `product.reserved` en SC20 y no se presentan como balance SC22.
- El aumento ocurre sólo cuando ORD-1012 se inserta realmente. Si
  `DEMO-001.onHand-reserved < 1`, V8 aborta atómicamente, conserva V7 íntegro y
  ofrece reintentar tras revisar disponibilidad; no resetea datos ni inventa
  stock. Este caso tiene prueba de rollback byte-exact.
- V8 no reescribe `ORD-1015` ni `RETURN-1015-1`.
- Para `ORD-1021`, V8 crea un registro `RETURN-1021-1` completo: motivo
  `ChangedMind`, resultado `Accepted`, una línea VLD-043 Standard por `$71.900`,
  etapa `Refunded`, refund `Refunded/$71.900` y eventos ordenados
  Submitted→Review→Approved→Received→RefundPending→Refunded fechados
  11/10/2026. La UI muestra `Reembolsada`, no inventa un wire
  `RETURN_RECEIVED`. Una colisión parcial o incompatible aborta la migración.
- V8 agrega `incidentStatus` cerrado al pedido: V7 sin incidencia=`None`, V7 con
  texto legacy=`Open`; fixtures: ORD-1018=`Resolved`, ORD-1019=`Open`,
  ORD-1022=`StockReview`. El texto legacy nunca decide la política.
- `DemoIncidentProjectionStep` es el único proyector para filas, filtros y
  comandos. Combina `order.incidentStatus` con `aftercare.incidents`
  correlacionados usando esta precedencia cerrada: cualquier wire Unknown →
  Unknown; cualquier Submitted o estado de pedido Open → Open; estado de pedido
  StockReview → StockReview; cualquier Closed o estado de pedido Resolved →
  Resolved; en otro caso None. Así una incidencia V7 conservada nunca se oculta.
- Gates obligatorios: roundtrip V7→V8→V8; V7 con carrito y pedido Pending previo;
  V7 sin disponibilidad; V7 con incidencia Submitted/Closed/Unknown y cambios
  posteriores en aftercare; colisiones actor/email/SKU/order/aftercare; fallo sin
  mutación parcial.

### Posventa de ORD-1015

- SC19 ya contiene `RETURN-1015-1`: una unidad de `LUM-042` aceptada y
  reembolsada por `$84.500`.
- Por lo tanto SC20 muestra `1 reembolsada / 1 disponible`, no “2 elegibles”.
- Esta proyección se calcula desde `aftercare`; no se guarda otro RMA sobre el
  pedido y no se habilita una transición RMA desde la cola.
- `ORD-1021` se proyecta únicamente desde su registro correlacionado: el fixture
  V8 válido muestra `Reembolsada`; ausencia, colisión o wire Unknown produce
  `Unknown` readonly y bloquea acciones.

### Retiro Demo sin contaminar Real

- `READY_PICKUP` es una capacidad exclusivamente Demo.
- El traductor compartido `ShipmentStatus.fromWire` no cambia y continúa
  convirtiendo ese wire productivo en `Unknown`.
- Demo modela retiro con `DemoPickupStage` cerrado (`None`, `Ready`, `Collected`,
  `Unknown`) y una proyección cerrada `DemoFulfillmentState`; la vista nunca
  compara el literal `READY_PICKUP`.
- `DemoOrder.pickupStage` se serializa como wire V8 y se decodifica en un único
  borde. V7 migra a `None`, salvo los fixtures añadidos por V8.
- ORD-1007 persiste `fulfillment=Pickup`, `shipment=Delivered`,
  `pickupStage=Collected`. ORD-1017 persiste `fulfillment=Pickup`,
  `shipment=Pending`, `pickupStage=Ready`.
- Proyección: Home exige pickup `None`; Pickup+Pending+Ready=`ReadyPickup`;
  Pickup+Delivered+Collected=`Collected`; combinaciones restantes y cualquier
  Unknown se muestran `Unknown` y son readonly.
- El comando unitario de retiro sólo acepta pago `Approved`, pedido `Paid`,
  modalidad `Pickup`, `pickupStage=Ready`, sin tracking y sin incidencia abierta.
  Produce atómicamente `pickupStage=Collected` y `shipment=Delivered`, sin
  carrier, guía, DNI, firma ni remito.

### Comandos unitarios

- No se reutiliza `DemoCommerce.advance()` en SC20.
- Cada paso es un objeto: `ShipDemoOrderStep`, `DeliverDemoOrderStep` y
  `CollectDemoPickupStep`.
- Cada comando autoriza antes de leer, captura identidad/sesión/revisión, valida
  precondiciones cerradas, vuelve a comprobar dentro de `state.run`, aplica una
  sola mutación y delega persistencia al writer existente.
- En fallo de persistencia se conserva el snapshot anterior, propuesta, filtros,
  selección y foco. Repetir el mismo comando exitoso no duplica historia.
- `SHIPPED` requiere tracking manual no vacío. `DELIVERED` preserva tracking.
  Nunca se inventa ni se atribuye una guía a un transportista.

| Paso | Origen y precondiciones cerradas | Incidencia/posventa | Efecto exacto | Resultado fixture |
|---|---|---|---|---|
| `ShipDemoOrderStep` | Home, Approved, Paid, Preparing, pickup None, tracking propuesto no vacío | sólo incidencia None/Resolved y sin devolución activa | shipment Shipped; tracking=propuesta; un evento | ORD-1013 habilita “Marcar enviado” |
| `DeliverDemoOrderStep` | Home, Approved, Paid, Shipped, pickup None, tracking existente | sólo incidencia None/Resolved y sin devolución activa | shipment Delivered; preserva tracking; un evento | ORD-1014 habilita “Marcar entregado”; ORD-1019 OPEN queda bloqueado y ofrece “Ver pedido” |
| `CollectDemoPickupStep` | Pickup, Approved, Paid, Pending+Ready, tracking vacío | sólo incidencia None/Resolved y sin devolución activa | Pending+Ready → Delivered+Collected; un evento | ORD-1017 habilita “Marcar retirado” |

Payment/Order/Fulfillment/Pickup/Incident/Aftercare Unknown, PaidStockReview,
Cancelled, una devolución activa o datos contradictorios bloquean. Repetir la
misma intención sobre el estado destino exacto es no-op; otro tracking o un estado
fresco distinto es conflicto y conserva la propuesta sin sobrescribir.

### Filtros, selección y exportación

- Búsqueda y filtros de pago, pedido, fulfillment, modalidad, incidencia y
  posventa son tipos cerrados con un único `fromWire` en el borde URL.
- Unknown se normaliza a criterio seguro y no habilita mutaciones.
- Los filtros se serializan en query params; back/forward/reload reproducen el
  resultado. Selección persiste al filtrar y distingue seleccionados visibles de
  seleccionados fuera del filtro.
- La cabecera usa checkbox semántico `checked/indeterminate`; móvil ofrece la
  misma selección mediante controles operables.
- Selección sólo alimenta exportación. No existen transiciones masivas.
- La cabecera selecciona o desmarca únicamente resultados visibles autorizados.
  No altera seleccionados ocultos por filtros.
- Exportar incluye todos los seleccionados autorizados, visibles u ocultos. El
  diálogo informa total y cantidad fuera del filtro antes de confirmar.
- Cero seleccionados deshabilita exportación. Restablecer filtros conserva la
  selección; `Limpiar selección` es una acción independiente.
- Gate: seleccionar dos, filtrar hasta ver uno, exportar ambos y desmarcar el
  visible conservando el oculto.
- CSV exacto, sin PII ni campos fiscales:

```csv
id,payment,shipment,total,incident
ORD-1012,PENDING,PENDING,198800,NONE
ORD-1019,APPROVED,SHIPPED,198800,OPEN
```

### Real

- Este corte no amplía `/user/orders` ni el backend.
- Real conserva su `AdminOrder` y sus acciones autoritativas actuales. El estado
  inicial RMA es `NONE`, el comando es `RECEIVED` y el resultado es
  `RETURN_RECEIVED`; null, `Unknown` o un RMA existente bloquean.
- No se publican compradores, contactos, fechas, modalidad, incidencias o
  cronología que el port Real no entrega.

## Superficie A

- Ruta `/demo/user/orders`; Admin y Operator pueden leer y ejecutar sólo comandos
  unitarios permitidos. Customer, Guest y Unknown no leen conteos ni filas.
- Doce filas/tarjetas con pago, pedido, fulfillment, modalidad, incidencia y
  posventa separados.
- Filtros deterministas: todos=12; pago PENDING=`ORD-1012`; incidencia
  OPEN=`ORD-1019`; pago PENDING + fulfillment SHIPPED=0.
- Selección inicial exacta `ORD-1012`/`ORD-1019` para el espécimen contractual.
- Cada fila y tarjeta navega a `/demo/user/orders/{id}`.

## Superficie B y accesibilidad

- B es evidencia externa, no una ruta ni contenido incrustado en A.
- El runtime Angular, no el HTML estático de Stitch, demuestra apertura/cierre de
  diálogos, `aria-modal`, nombre, foco inicial, trampa Tab/Shift+Tab, Escape,
  aislamiento del fondo y restauración.
- Desktop, tablet y móvil se validan en navegadores reales a 1440, 768 y 390.
  Móvil conserva doce registros, seis ejes, navegación, filtros, selección y
  exportación; no es una segunda lista decorativa.
- Texto informativo alcanza 4.5:1. Ningún claim “verificado” se acepta sin axe,
  teclado y captura de la implementación ejecutable.

## Gates de implementación

1. decoder/migración V8, rollback e idempotencia focales;
2. tipos cerrados y tests de `Unknown` para todos los conjuntos finitos;
3. matriz de autoridad antes de lectura y dentro del comando;
4. preservación byte-exact de todo salvo estado/tracking/historia declarados;
5. filtros URL, selección fuera de filtro y CSV exacto;
6. diálogos y navegación por teclado con restauración de foco;
7. 1440/768/390 + text-200% + axe sin pérdida funcional;
8. suite Demo completa, build Demo, verify y doble review exact-SHA.
