## Decisión de alcance y límites

POSC-002 añade la frontera de autenticación/autorización y privilegios que necesitarán los cortes POSC-003/004, sin habilitar tráfico live ni cambiar el wire adjudicado. Conserva instalación single-tenant por VM y companion 0..1; BlackStore no accede a la base StoreCore. La base V5 ya tiene `blackstore_companions`, `blackstore_companion_credentials`, índices únicos de companion vivo y credencial activa. El `JdbcBlackStoreCompanionStore.assertBound` actual compara sólo el `X-Client-Instance-Id` y la fila viva; eso no autentica al caller y **no** basta para GO. El token `scbs1` de la rama dirty no se porta ni redefine el YAML pinneado.

No se crean credenciales de producción ni se activa la capability. **Decisión de alcance:** POSC-002 sí cambia mínimamente los puertos/adapters existentes de Tx-A, Tx-B, commit y release para transportar el principal validado y revalidar el guard dentro de cada transacción real. No cambia las reglas comerciales de reserva, precio, stock o ledger, cuyo porteo/refactor de dominio queda en POSC-003/004. La prueba debe observar el engine real, no un guard aislado. No se habilita worker/purge. El diseño final de tablas, owners y funciones queda sujeto a review de seguridad y preflight PG16. El adaptador fiscal permanece externo.

## Identidad de servicio y puerto de secretos

El `Authorization: Bearer` es un secreto opaco aleatorio de al menos 256 bits, emitido una sola vez por el provisioning autorizado y entregado a BlackStore fuera del repo. **No lleva sintaxis `scbs1` ni claims parseables por el cliente.** BlackStore ya usa `StoreCoreHttpTransport(settings, resolveToken = { ref -> ... })`: `settings.tokenRef` se resuelve en cada llamada, el transporte emite `Bearer <valor>` y no lo loguea. El fixture end-to-end de POSC-002 debe usar ese mismo puerto/HTTP real en loopback con token sintético, `X-Client-Instance-Id` coincidente y digest pinneado; no debe introducir formato nuevo ni editar BlackStore.

El puerto de aplicación `CompanionCredentialVerifier.verify(rawBearer): VerifiedCompanionPrincipal | Invalid | ProviderUnavailable` consume bytes de bearer sin loguearlos. Se propone agregar a la credencial `token_fingerprint` SHA-256 UNIQUE de token aleatorio de alta entropía y metadata inmutable `scopes` + `service_role` (`SERVICE`/perfil operativo no equivalente a USER humano). El fingerprint sólo selecciona una fila; **no autentica**. `CompanionSecretProvider.resolve(credential_secret_ref): SecretBytes | Missing | TransientFailure` recupera el valor y el verifier compara bytes en tiempo constante, borra buffers cuando sea posible y luego verifica credential `ACTIVE`, `auth_ready=TRUE`, version, companion binding y estado. Scopes viven del lado servidor asociados al token opaco y se congelan en el principal, nunca proceden de headers. `Missing`/comparación fallida son identidad inválida; `TransientFailure` (timeout/indisponibilidad) es fallo temporal de servidor, no una falsa revocación. Si no se puede garantizar referencia resoluble, token de 256 bits y store del fingerprint en el provider/DB disponibles en la VM por cliente, el provisioning y el GO quedan bloqueados; no hay fallback a header ni token de prueba dirty.

`CompanionTokenGenerator.next256Bits()` (CSPRNG de infraestructura) genera el token plano en StoreCore, nunca a partir de un body de cliente ni de BlackStore. `CompanionSecretProvider.prepare(requestId, rawBearer)` es idempotente por `requestId`: crea una ref durable recuperable y, ante retry, confirma la **misma** ref/fingerprint sin emitir un segundo secreto ni activar token; `resolve` confirma el valor antes de DB y `discard(ref, requestId)` compensa preparación fallida. La ref se guarda en `blackstore_companion_credentials.credential_secret_ref`, nunca el token plano. La respuesta inicial protegida puede mostrar el token **una sola vez** al USER ADMIN para cargarlo en el secret manager de BlackStore bajo `settings.tokenRef`; la configuración BlackStore contiene sólo la ref y su `resolveToken` existente devuelve los mismos bytes. Los tests conectan ambos lados con providers sintéticos y transporte loopback real, sin modificar ese repo ni usar secretos live. El replay administrativo devuelve sólo metadata (no bearer/ref secret) y, si se perdió la primera entrega, exige una rotación explícita. La cache de lookup puede ser negativa; no se permite cache positiva de autorización que sobreviva a commit de revocación. Redacción de logs, métricas, tracing y errores es requisito de test.

La verificación produce un principal **inmutable** para toda la operación: `clientInstanceId`, `companionId`, `credentialId/version`, `serviceRole` y scopes autorizados. El `X-Client-Instance-Id` debe coincidir con el principal, nunca lo crea ni lo amplía. `X-Device-Id`, `X-Sale-Id` y `X-Operation-Id` son claves contractuales/idempotentes, no credenciales. El servidor revalida versión/estado bajo barrera transaccional en cada operación mutante; un caché positivo no puede sobrevivir a revocación. Companion `DISABLED`/`REVOKED`, credential `REVOKED`, capability `DISABLED`, scope ausente o kill switch deniegan. La fila de capability y sus reglas existentes siguen siendo autoridad; no se activa por sembrar una credencial.

El puerto `CompanionAuthorizationGuard.authorize(principal, action, requiredScopes)` acepta el principal y una acción concreta, no un `clientInstanceId` arbitrario. El filtro/adapter HTTP autentica antes de llamar al use case; el port de saga recibe ese mismo principal y lo revalida bajo locks en Tx-A/Tx-B/commit/release. GET/reconcile usa snapshot de lectura consistente y revalida antes de leer, sin romper su futuro gate read-only. `X-Actor-Role` es **sólo metadata de auditoría no verificada**, nunca prueba rol humano ni amplía scopes.

**Error matrix pinneada, sin wire nuevo:** bearer ausente/malformado/desconocido/revocado o secret ref permanentemente ausente → HTTP 401/`UNAUTHORIZED`, `retryable=false`; bearer válido pero header de instancia ajeno, scope ausente, intento de `includeCost=true` sin delegación verificable o companion DISABLED/REVOKED → HTTP 403/`FORBIDDEN`, `retryable=false`; capability `DISABLED`/kill switch → HTTP 403/`CAPABILITY_DISABLED`, `retryable=false`; timeout/indisponibilidad del provider **después de identificar la ref** → HTTP 500/`INTERNAL`, `retryable=true`, sin ejecutar Tx-A ni revelar si la ref existe. Header contractual ausente/malformado, `X-Override-Reason` inválido o `X-Actor-Role` inválido para override → HTTP 400/`VALIDATION`, `retryable=false` tras autenticar. Todos los JSON salvo 304 usan `BaseResponse`: `code=HTTP`, `data=null`, `errorCode`, `retryable`, `message`, `traceId`. Orden de precedencia: autenticar → resolver disponibilidad del provider → comparar binding/estado/scope/capability → validar headers/body contractuales → rate/operación; ninguna denegación deja claim o mueve stock. No convertir error temporal del provider en 401 ni reintentar POST a ciegas: BlackStore usa GET de recuperación conforme al contrato.

## Barrera de concurrencia: revocación, disable y Tx-A/Tx-B

La autenticación HTTP previa es preliminar. El `JdbcBlackStoreSagaEngine` actual no recibe principal en Tx-A/Tx-B/commit/release: POSC-002 **debe** cambiar de forma mínima `BlackStoreSagaPort` y callers para pasar `VerifiedCompanionPrincipal`, llamar al guard en **cada** transacción real antes del efecto y comparar `credentialId/version`, scopes y binding con la fila bloqueada. Un unit test del filtro no basta. No se cambia el algoritmo de cuádruple, stock, ledger ni el wire; si el adapter no puede transportar el principal a todas las rutas mutantes, POSC-002 es NO-GO, no se difiere silenciosamente a POSC-003/004.

**Port SQL concreto de guard POS:** `PosCompanionGuardPort.authorizeForEffect(principal, action)` invoca una función estrecha `pos_companion_effect_guard(p_companion_id BIGINT,p_credential_id BIGINT,p_credential_version INTEGER,p_action VARCHAR)` como **primera consulta en la transacción mutante**. Una función hermana `pos_companion_read_guard(...)` sin locks sirve lectura RO. Ambas aceptan sólo las acciones BLACKSTORE_INTEGRATION presembradas y mapean action→scope internamente; parámetros no forman SQL dinámico ni seleccionan otro módulo. La función de efecto, `SECURITY DEFINER`, tiene owner `storecore_pos_guard_owner` NOLOGIN diferente de runtime/admin, `search_path=pg_catalog,pg_temp`, referencias `public.` calificadas, `REVOKE EXECUTE FROM PUBLIC` y `GRANT EXECUTE` de firma exacta sólo a `storecore_runtime`. Su owner recibe SELECT y privilegio `UPDATE` mínimo sobre una columna de lock por cada action/config/switch/companion/credential (PostgreSQL 16 lo exige para `FOR SHARE`), sin funciones de DML ni grants heredados; runtime recibe **EXECUTE**, no UPDATE directo. El definer ML para MARKETPLACE_ML/SYNC no cubre estos objetos POS. Si el manifiesto/PG16 no demuestra ese aislamiento, no se implementa un `FOR SHARE` directo desde runtime.

**Orden global compartido con ML-DSP-000B para cualquier efecto o administración:** (1) filas de `capability_actions` de los módulos implicados, orden `module_code,action_code`; para POS se bloquean todas las acciones BLACKSTORE_INTEGRATION existentes (ancla persistente aun cuando no hay switch activo), lectura `FOR SHARE` y administración `FOR UPDATE`; ausencia de acción requerida falla cerrado, (2) `module_configurations` de instalación, `FOR SHARE/UPDATE`; ausencia falla cerrado, (3) `capability_kill_switches` vigentes/efectivos por `module_code,action_code,id`, (4) `blackstore_companions` por id, (5) credential activa por `companion_id,credential_version`, (6) advisory de cuádruple y saga, (7) variantes/balances/reservas en orden del engine. Si un comando abarca ML y POS toma todas las action rows requeridas ordenadas antes de ambas configs; nunca vuelve a una clase anterior. El `JdbcCapabilityService.decide` publicado hoy hace **switch→config→action**, y la administración V3 toma config/switch por otro orden: ambos caminos deben converger al orden action→config→switch en el mismo delta coordinado de ML/POS antes de activar efectos. No se llama al `decide` actual dentro de la nueva barrera porque invertiría locks.

El bloqueo de **todas** las action rows POS más config serializa también la ausencia de switch: create/replace/remove debe tomar el ancla `FOR UPDATE` **antes** de insertar/cambiar switch. No basta `SELECT ... FOR SHARE` sobre cero filas. El guard mutante se ejecuta únicamente en transacción explícita `READ COMMITTED`; el adapter configura y comprueba ese aislamiento y la función `VOLATILE` exige `current_setting('transaction_isolation')='read committed'`, rechazando cualquier transacción ambiente `REPEATABLE READ` o `SERIALIZABLE` antes del primer lock. La función no fusiona lecturas en un CTE ni en una sentencia SQL única: primero adquiere las action rows persistentes `FOR SHARE` en orden fijo; **en una sentencia PL/pgSQL posterior**, con snapshot nuevo de READ COMMITTED, lee/bloquea la config `FOR SHARE`; **en otra sentencia posterior** lee los switches efectivos, y después companion y credential por sentencias secuenciales. El admin compartido usa también READ COMMITTED y toma las mismas action rows `FOR UPDATE` antes de leer/cambiar config o insertar/reemplazar/remover switch. Así, si admin confirmó durante la espera por el ancla, la sentencia de lectura posterior observa su cambio. Ninguna decisión se reutiliza desde el snapshot previo al lock, incluido el `JdbcCapabilityService.decide` actual; si falta una fila o el estado es inválido, falla cerrado. Esta semántica del guard y del admin es parte del **único delta compartido ML/POS** y debe verificarse con ambas familias de efectos, no sólo con POS. Revocar credential/companion usa el mismo prefijo action→config→switch→companion→credential; disable/kill usa el prefijo action→config→switch. La regla observable: luego de confirmar revocación o `DISABLED`, ningún efecto nuevo con principal viejo confirma. Un efecto que tomó el guard antes obliga a la administración a esperar; éste confirma o revierte antes de revocación. Probar timeout/deadlock con reintento de la **transacción completa**, jamás saltando autorización.

Validar schema, bearer y header antes de Tx-A. Tx-A vuelve a autorizar bajo barrera y crea `PENDING`+`request_hash` durable sólo si sigue autorizado. Tx-B —incluido re-POST de un `PENDING`— toma la barrera de nuevo antes de lock de saga/variantes, revalida versión/capability y sólo entonces reserva. Commit y release hacen igual antes de cualquier ledger/balance. Si revocación gana entre Tx-A y Tx-B, no se reserva; PENDING conserva evidencia y el worker existente lo recupera/expira según contrato.

**GET/reconcile reciben también `VerifiedCompanionPrincipal` en el port de lectura**, no sólo en el controller. Cada consulta de saga, receipt y tombstone filtra `client_instance_id=principal.clientInstanceId`; GET ajeno devuelve el 404 contractual y reconcile clasifica receipt ajeno como `unknownReceipts`, sin revelar estado o tombstone de un companion anterior. Re-pair A(revocado)→B(nuevo UUID) no permite que B lea historia de A. La primera sentencia SQL de la transacción `readOnly + REPEATABLE_READ` es `pos_companion_read_guard`: adquiere el snapshot MVCC **sin FOR SHARE ni esperar lock de action**, lee capability/switch/companion/credential en ese mismo snapshot y luego GET/reconcile mantiene esa fotografía hasta terminar. No abrir transacción RR ni ejecutar otro SELECT antes de este guard; un snapshot adquirido antes de esperar una action row podría omitir un kill switch recién insertado. Si admin confirma antes de esa primera sentencia, la lectura deniega; si confirma después, la lectura ya iniciada puede terminar. PIC-006A verifica orden, read-only y carrera admin-wins sin escritura; ninguna llamada usa el `JdbcCapabilityService.decide` switch→config→action actual.

## Administración protegida y state machine 0..1

**Entrada elegida:** rutas operacionales internas `/internal/admin/blackstore-companion/{pair,activate,suspend,rotate,revoke}` y `GET /internal/admin/blackstore-companion/commands/{correlationId}`, no parte de los siete paths públicos ni del YAML BlackStore. El adapter reutiliza `RequestAuth.requireSameOrigin(http)` y `RequestAuth.admin(http)`; la mutación usa el coordinador admin Tx-S/Tx-C definido abajo, **no** `IdentityMutationCoordinator.execute` del baseline. La sesión es realm `USER` con rol `ADMIN`, no CUSTOMER ni `X-Actor-Role`; cada mutación exige `X-CSRF-Token`, `reason` no vacío y `correlationId` UUID único. El GET de estado también exige USER ADMIN y mismo origen; no devuelve token ni secret ref. Las funciones de preparación/attach/abort son pasos **internos del mismo use case** y no endpoints HTTP invocables por BlackStore. La opción CLI, si se usa para bootstrap, invoca el **mismo** use case tras autenticar USER ADMIN; nunca SQL manual/credenciales DB de superuser. No se expone al companion. Un port `CompanionAdministrationPort` recibe `InternalUserPrincipal` obtenido del adapter, expectedVersion y comando tipado, no `actorId` del body.

El adapter admin usa conexión/pool operacional separada cuyo login hereda sólo `storecore_companion_admin` NOLOGIN; el pool público `storecore_runtime` no hereda ese rol ni recibe EXECUTE de las funciones admin. Sólo el rol admin tiene EXECUTE sobre funciones estrechas de pairing, credential y auditoría, con owner NOLOGIN dedicado y `search_path` seguro. El actor USER se autentica y Tx-S consume/rota CSRF duraderamente **antes** de prestar esa conexión; la función SQL recibe `p_actor_user_id` únicamente para auditoría y confirma USER activo/ADMIN, sesión e intent admitido, pero ese parámetro jamás reemplaza autenticación en el adapter. La operación admin y su audit/conflicto se confirman atómicamente en Tx-C del pool admin. Si se pierde la respuesta después del commit, el mismo `correlationId` devuelve el resultado persistido sin repetir efecto; se obtiene un CSRF nuevo por la ruta de identidad autenticada. El contrato de configuración del datasource/secret operacional es dependencia explícita; si no está disponible o no se puede aislar de runtime, no hay GO de implementación.

Firmas SQL propuestas (nombres definitivos sujetos a preflight/review): `companion_admin_pair(p_actor_user_id BIGINT,p_client_instance_id UUID,p_token_fingerprint CHAR(64),p_secret_ref VARCHAR,p_scopes TEXT[],p_service_role VARCHAR,p_correlation UUID,p_reason VARCHAR)`; `companion_admin_activate(p_actor_user_id BIGINT,p_companion_id BIGINT,p_expected_state VARCHAR,p_expected_credential_version INTEGER,p_correlation UUID,p_reason VARCHAR)`; `companion_admin_suspend(p_actor_user_id BIGINT,p_companion_id BIGINT,p_expected_state VARCHAR,p_expected_credential_version INTEGER,p_correlation UUID,p_reason VARCHAR)`; `companion_admin_rotate(p_actor_user_id BIGINT,p_companion_id BIGINT,p_expected_state VARCHAR,p_expected_credential_version INTEGER,p_new_token_fingerprint CHAR(64),p_new_secret_ref VARCHAR,p_new_scopes TEXT[],p_new_service_role VARCHAR,p_correlation UUID,p_reason VARCHAR)`; `companion_admin_revoke(p_actor_user_id BIGINT,p_companion_id BIGINT,p_expected_state VARCHAR,p_expected_credential_version INTEGER,p_correlation UUID,p_reason VARCHAR)`. Estas cinco funciones de **efecto** usan action→config→switch→companion→credential, CAS, estados esperados y audit append-only en la misma Tx; los cuatro entry points de Tx-P/status/abort que siguen sólo gestionan comandos y no simulan un efecto. Ningún SQL del cliente recibe identificador de tabla/módulo arbitrario.

**Entry points obligatorios de Tx-P, acotados al owner admin:** `companion_admin_prepare_command(p_actor_user_id BIGINT,p_operation_kind VARCHAR,p_client_instance_id UUID,p_companion_id BIGINT,p_expected_state VARCHAR,p_expected_credential_version INTEGER,p_scopes TEXT[],p_service_role VARCHAR,p_correlation UUID,p_reason VARCHAR,p_command_hash CHAR(64)) RETURNS TABLE(command_state VARCHAR,command_hash CHAR(64))`; `companion_admin_attach_secret(p_actor_user_id BIGINT,p_correlation UUID,p_command_hash CHAR(64),p_token_fingerprint CHAR(64),p_secret_ref VARCHAR) RETURNS VARCHAR` (`READY` o `ABORTED`); `companion_admin_command_status(p_actor_user_id BIGINT,p_correlation UUID) RETURNS TABLE(command_state VARCHAR,operation_kind VARCHAR,companion_id BIGINT,credential_version INTEGER,token_fingerprint CHAR(64))`; `companion_admin_abort_command(p_actor_user_id BIGINT,p_correlation UUID,p_command_hash CHAR(64),p_reason VARCHAR) RETURNS VARCHAR` (`ABORTED`, o conflicto si ya completó). Los argumentos opcionales sólo son NULL cuando su `operation_kind` los excluye; la función valida combinaciones y valores. `p_operation_kind` se limita a `PAIR|ROTATE`, `p_service_role` y scopes al vocabulario permitido, y las funciones nunca aceptan módulo, action, tabla, SQL, bearer plano ni actor de un body público. Todas devuelven sólo metadata, jamás token o secret ref. Cada entry point vuelve a comprobar en DB `users.active` y pertenencia a `roles.code='ADMIN'` por `user_roles`, además de la sesión USER ADMIN+CSRF comprobada por el adapter; actor inexistente/inactivo/OPERATOR falla cerrado.

La fila durable de comando guarda `correlation_id` único, actor, operación, campos normalizados del comando, `command_hash`, estado `PENDING|READY|COMPLETED|ABORTED`, fingerprint/ref sólo desde `READY`, resultado y timestamps; audit append-only registra prepare, attach, complete y abort con actor y motivo, sin secreto. `prepare_command` calcula/contrasta la misma representación normalizada que el hash aportado por el adapter: en reintento exige **igualdad de todos los campos guardados y del hash**, no confía sólo en el hash; mismatch → conflicto sin cambio. `attach_secret` toma la fila `FOR UPDATE`, exige mismo actor, hash y `PENDING`, adjunta una única pareja fingerprint/ref cuyo provider ya verificó; retry idéntico devuelve `READY`, pareja distinta falla. `status` sólo lee comando del actor administrador autenticado y no revela la ref; `abort` toma la fila `FOR UPDATE`, permite sólo `PENDING|READY`, deja evidencia `ABORTED` y programa `discard` de la ref fuera del commit; retry idéntico es idempotente. `pair`/`rotate` toman la fila `READY` del mismo actor/correlation, verifican hash, fingerprint/ref/scopes/role y estado CAS, aplican registry + audit y marcan `COMPLETED` **en la misma Tx-C**; replay devuelve metadata. `activate`/`suspend`/`revoke` usan su propio correlation y audit atómico, sin Tx-P ni secreto nuevo. Una respuesta perdida se resuelve por `command_status`; no regenera ni reexpone token.

**Transiciones:** sin companion → `DISABLED` con una credential preparada `ACTIVE` pero no utilizable; `DISABLED→ACTIVE` sólo si capability lo permite, secret ref resuelve y autorización USER ADMIN/CAS valida; `ACTIVE→DISABLED` como suspensión administrativa serializada; `DISABLED|ACTIVE→REVOKED` terminal con `revoked_at`, revoca la credencial activa y nunca reutiliza clientInstanceId/token. Una instalación conserva a lo sumo un companion no-REVOKED por índice parcial; no se permite volver de REVOKED a ACTIVE. Re-pair después de REVOKED usa nuevo `clientInstanceId` y token. Credential `ACTIVE→REVOKED` sólo dentro de rotate/revoke; rotate en companion no-REVOKED revoca anterior e inserta `version+1` activa en una Tx, sin ventana con dos activas. `expected_credential_version` y `expected_state` son CAS obligatorios.

**Provisioning idempotente de pair/rotate:** Tx-P prepara una fila admin `PENDING` única por `correlationId` con hash **sólo del comando enviado por USER ADMIN** (clientId, estado/versión esperados, scopes, role, reason), antes de generar token/ref. Correlation igual+hash distinto → conflicto sin efecto; igual+hash igual → retoma/consulta la misma operación. Tras Tx-P, se genera un único token CSPRNG para esa operación y `prepare(correlationId, token)` es idempotente; la preparación persiste fingerprint/ref asociados a la fila admin sin publicar credencial. Tx-C toma fila admin y guards de estado, verifica provider ref, hace pair/rotate+audit+resultado y marca COMPLETED en **una** transacción. Un retry no regenera token ni secreto; si un crash ocurre entre generación y persistencia de ref, el provider debe poder retomar por requestId sin entregar otro token, o el comando se marca ABORTED y requiere nueva correlation; nunca se activa un secreto distinto bajo mismo hash. El replay COMPLETED devuelve metadata solamente, jamás reexpone bearer. Si la primera respuesta con bearer se pierde, recuperación vía metadata y nueva rotación explícita. Overflow de INTEGER en versión aborta antes de revocar, exige migración revisada de tipo, nunca wraparound. Fallo antes de Tx-C descarta la ref; fallo ambiguo tras commit consulta correlation/fingerprint/version antes de compensar, nunca revoca la credencial ganadora. Falla de descarte deja ref huérfana aislada para limpieza auditada. No se borran historia, audit ni refs aún en uso.

## Cierre end-to-end de la administración V3 compartida

**Evidencia del baseline:** `JdbcCapabilityService` implementa `CapabilityDecisionPort` y `CapabilityAdministrationPort` con el mismo `JdbcTemplate`. Sus cuatro comandos (`changeState`, `createKill`, `removeKill`, `replaceKill`) llaman las cuatro funciones V3 usando el datasource runtime y `@Transactional`; `CapabilityController` los ejecuta dentro de `IdentityMutationCoordinator.execute`, que verifica y rota CSRF en una transacción de identidad del mismo datasource. Revocar `EXECUTE` a runtime sin cambiar **servicio, controller, coordinador y wiring transaccional** rompe los cuatro endpoints aunque el nuevo DDL sea correcto. La operación `list` y las decisiones de lectura pueden conservar el datasource runtime con SELECT acotado; las mutaciones se extraen a un adapter `CapabilityAdministrationPort` que utiliza exclusivamente un `JdbcTemplate` y un `PlatformTransactionManager` del pool administrativo.

El pool capability admin usa un login DB operacional distinto del login runtime y del migrator, miembro sólo de `storecore_capability_admin` NOLOGIN. El pool companion admin usa otro login, miembro sólo de `storecore_companion_admin` NOLOGIN, como se define arriba; no se mezclan sus roles. Credenciales y URLs proceden de configuración/secret provider externo de la instalación, nunca del repo, del body HTTP, de `SET ROLE` ni de una conexión runtime prestada. Los pools no heredan uno del otro, de `storecore_runtime`, de owners definer ni de `storecore_migrator`; readiness y los comandos fallan cerrados si falta el pool correspondiente o su identidad efectiva difiere. El pool admin no ejecuta Flyway. Los puertos de aplicación tipados no exponen JDBC al controller; la implementación selecciona por inyección explícita el manager/pool administrativo, sin depender de `@Primary` ni de propagación implícita de la transacción runtime.

El controller autentica USER ADMIN y mismo origen. El `IdentityMutationCoordinator.execute` actual no puede envolver SQL admin en su transacción runtime: `verifyCsrf` sólo verifica y bloquea una fila; al terminar esa transacción el token sigue activo. El shared delta define un coordinador admin específico con **Tx-S runtime durable antes de Tx-C admin**. Tx-S bloquea `identity_sessions` y el token CSRF activo de la sesión USER, revalida sesión/actor ADMIN y hash del token recibido, inserta o confirma un intent único por `correlationId` con `session_id`, `actor_user_id`, tipo, módulo/objetivo, `request_hash` y campos normalizados; exige igualdad completa en un replay. En esa misma Tx-S retira el token mediante CAS `retired_at IS NULL`, genera/persiste el siguiente token CSRF y confirma intent+consumo+rotación atómicamente. Un token usado para correlation A no puede admitir correlation B: ambas solicitudes se serializan por lock de sesión/token, la segunda observa el token retirado y falla 403 sin abrir admin Tx. No se mantiene lock runtime entre Tx-S y Tx-C ni se usa `SET ROLE`.

Tx-C, en la conexión/pool admin, comprueba el intent durable por correlation, actor, sesión y hash mediante función definer con SELECT mínimo, revalida USER activo/ADMIN y sesión USER vigente, toma guard action→config→switch, aplica CAS/mutación/audit y guarda el resultado de comando en un único commit. Un crash tras Tx-S y antes de Tx-C deja intent admitido sin efecto: con una sesión válida el mismo USER obtiene CSRF nuevo por la ruta de identidad existente y reenvía **igual correlation y payload**, consumiendo ese nuevo token en otra Tx-S; el intent existente se valida y Tx-C completa una sola vez. Si Tx-C confirmó y se perdió la respuesta, el replay devuelve el resultado durable sin nueva mutación/audit; el GET interno de status permite confirmar el resultado. Si la sesión original expiró/revocó, Tx-C no ejecuta; un USER ADMIN reautenticado puede consultar por correlation como mismo actor, pero un nuevo intento de efecto requiere flujo de recuperación/intent revisado, no cambia `session_id` del intent ni duplica con correlation nueva a ciegas. Fallo del pool admin no revierte Tx-S: se informa retryable y el intent queda recuperable. El siguiente CSRF se devuelve sólo tras confirmar Tx-S; si se pierde, se renueva mediante el endpoint de identidad autenticado. La lectura `list` posterior a Tx-C ocurre en una conexión runtime nueva. Las pruebas deben demostrar la máquina de estados y su recuperación; hasta entonces el corte es NO-GO.

**Precedencia de recuperación de Tx-C:** para una solicitud con sesión USER ADMIN actual y `correlationId`/actor/hash/campos coincidentes, la función consulta primero el resultado durable. Si ya está `COMPLETED`, devuelve ese resultado **antes** de exigir vigencia de la sesión original o tomar CAS/guard de efecto; una sesión nueva del mismo actor sólo puede leer/repetir ese resultado, nunca ejecutar el comando pendiente asociado a otra sesión. El intent de Tx-S es evidencia inmutable: el GET de status hace sólo SELECT y devuelve `PENDING`/`COMPLETED`/`ABORTED` según el registro de comando, sin lock mutante ni terminalización. Para un `PENDING` con sesión original expirada/revocada, el mismo actor reautenticado usa un **POST interno de recuperación** con correlation original y CSRF actual: una Tx-S de recuperación consume/rota ese CSRF sin cambiar la sesión ni los campos del intent original; Tx-C toma lock del registro de comando, vuelve a consultar terminal y, si sigue pendiente, persiste `ABORTED` sólo en comando/resultado con audit, sin ejecutar el efecto. Tx-C normal y recuperación compiten bajo el mismo lock: si ganó un `COMPLETED`, ambos devuelven ese resultado; si ganó `ABORTED`, ningún Tx-C posterior aplica efecto. El login admin tiene sólo EXECUTE de la función estrecha de recuperación y el owner admin usa el DML de comandos ya previsto; runtime no recibe UPDATE de intent. Un nuevo efecto exige nueva sesión, CSRF y correlation tras constatar `ABORTED`; `correlationId` antiguo no se reabre. Se prueban crash después de Tx-S, sesión expirada antes de Tx-C, GET sin writes, carrera recuperación/Tx-C y respuesta perdida después de COMMIT.

**Decisión de idempotencia capability:** las cuatro mutaciones HTTP de `CapabilityController` exigen `correlationId` UUID aportado por el cliente administrador; el fallback actual `UUID.randomUUID()` y el campo nullable dejan de ser válidos para ese contrato y ausencia/malformación produce 400 sin abrir Tx admin. El shared delta agrega un registro durable de comando con UNIQUE(`correlation_id`), actor USER, tipo de operación, módulo/acción/ID objetivo, parámetros normalizados, `request_hash`, resultado tipado y estado terminal. En la **misma** transacción del pool capability admin, la función estrecha adquiere ese claim, compara hash **y campos**, ejecuta guard/CAS, mutación y audit, y persiste resultado terminal; igual correlation+payload devuelve exactamente el resultado guardado sin nuevo cambio/audit, distinto payload devuelve conflicto sin efecto. Un resultado `COMPLETED` perdido se recupera con GET status o replay bajo sesión USER ADMIN actual del mismo actor y CSRF vigente, incluso tras reautenticación; un intent admitido sin resultado sólo retoma Tx-C con su sesión original aún vigente. No se reutiliza el audit V3 como índice de idempotencia ni se regenera correlation en servidor. El controller y su cliente interno se actualizan juntos; hasta demostrar este contrato y las carreras de replay en PG16/HTTP, el shared cutover es NO-GO.

**Privilegios y owner del shared delta:** las cuatro firmas V3 pierden EXECUTE efectivo de PUBLIC, runtime y ambos roles admin. No hay wrapper que vuelva a invocar V3: sus cuatro llamadas en `JdbcCapabilityService` se sustituyen por entry points nuevos para **todos** los módulos administrables; ML/POS exigen su guard action-aware y los demás conservan sus invariantes de transición/audit sin un camino V3 directo. El owner V3 `storecore_migrator` NOLOGIN queda sólo para historia/migración, jamás es miembro del login de aplicación. El login capability admin obtiene EXECUTE sólo sobre entry points estrechos de los cuatro comandos y consulta de resultado por correlation; no tiene DML directo sobre `capability_actions`, `module_configurations`, `capability_kill_switches`, intent/comando/audit ni SELECT de `users/roles/user_roles/identity_sessions`. El owner `storecore_capability_admin_owner` NOLOGIN, sin membresía de runtime/migrator, recibe SELECT mínimo de USER/roles, sesión USER e intent para verificar actor/Tx-S; SELECT y privilegio de lock/UPDATE mínimo sobre action/config/switch; DML necesario sobre config/switch/comandos e INSERT append-only en audit. El runtime identity recibe únicamente INSERT/SELECT mínimo en intents y DML ya autorizado de sesión/CSRF para Tx-S; el owner companion admin recibe SELECT mínimo del mismo intent/sesión para sus nueve entry points, nunca DML directo del login companion admin. Toda función definer usa tablas `public.` calificadas, SQL estático y `search_path=pg_catalog,pg_temp`, sin módulo/acción arbitrarios fuera de whitelist. Inspeccionar owner, membresías, default grants y secuencias nombradas para demostrar privilegio efectivo, no sólo GRANT declarativo.

El rol `storecore_companion_admin` conserva EXECUTE exclusivamente sobre las nueve firmas POS enumeradas abajo, sin EXECUTE de V3 ni de capability admin; el owner companion NOLOGIN mantiene sus permisos mínimos de registry/comandos/audit y de guard action→config→switch. Las funciones POS `prepare`, `attach`, `status`, `abort`, `pair`, `activate`, `suspend`, `rotate` y `revoke` se ejercen desde ese pool con actor USER ADMIN validado en HTTP y DB; ninguna se llama con el datasource runtime. El actor USER y el companion son identidades distintas. Los dos pools admin toman las mismas action rows `FOR UPDATE` antes de config/switch, por lo que un disable/kill compartido, una revocación y un efecto POS tienen un orden serializable observable. El pool runtime sólo recibe EXECUTE de guards estrechos y DML operacional enumerado en el manifiesto.

**Aislamiento por flujo:** la administración capability/POS y los efectos POS usan transacciones explícitas `READ COMMITTED` con guard `VOLATILE` y lecturas posteriores al ancla; los GET/reconcile POS conservan `readOnly + REPEATABLE_READ` sin locks. El código publicado de `JdbcCapabilityService.decide` usa `REPEATABLE_READ` para decisiones ML/core y toma switch→config→action. ML-DSP-000B exige snapshot action→config→switch y carrera admin-wins, pero aún no aporta prueba de que una transacción ML `REPEATABLE_READ` vea un switch insertado mientras espera el ancla. No reutilizar el guard POS `READ COMMITTED` dentro de una transacción ML RR ni degradar silenciosamente el aislamiento de ML: su owner debe resolver en su SDD la adquisición de snapshot/revalidación y demostrar la carrera PG16 con switch inicialmente ausente, o ML-DSP-000B sigue NO-GO. El shared delta puede establecer roles y orden de locks sin atribuir a POS la validación de la semántica ML pendiente.

**Orden de corte:** (1) inventariar head Flyway, funciones V3, owners, grants efectivos y wiring real de los cuatro endpoints; (2) aprobar un único delta compartido ML/POS con firma/owner/rol/orden de locks y tests PG16, seguido del delta POS credential/companion en versión libre distinta; (3) implementar y verificar pools, puertos, coordinador CSRF y funciones nuevas con capability admin/companion admin en limpio y upgrade; (4) en el mismo corte transaccional de migración, conceder EXECUTE de firmas nuevas a los roles admin y revocar V3 de PUBLIC/runtime/admin, cerrando wrappers genéricos para ML/POS; (5) desplegar adapter nuevo coordinado con readiness administrativa cerrada durante el cambio, y abrir comandos sólo después de probar pool efectivo, HTTP y rollback operativo. No publicar un estado donde V3 queda revocado y el endpoint viejo sigue activo; tampoco mantener V3 público como fallback. La migración de esquema no activa capability ni integraciones. Si el despliegue necesita continuidad sin ventana de mantenimiento, diseñar y revisar una transición adicional antes de ejecutarla.

**Gate PG16/HTTP adicional:** en base limpia y upgrade V1–V7 con datos, probar las cuatro rutas `CapabilityController` de estado y kill create/remove/replace por HTTP USER ADMIN+CSRF con pool admin efectivo, resultado/audit y `list` posterior; 403 para CUSTOMER/OPERATOR/CSRF inválido, fallo cerrado si falta pool admin, y ningún efecto duplicado tras respuesta perdida/retry de correlation. Un login runtime puro, uno sin rol y el login companion admin fallan al invocar cada firma V3 y cada función capability admin; el login capability admin falla al invocar las nueve funciones POS y DML directo. Un login companion admin ejerce las nueve POS y falla sobre V3/capability admin; su owner sí verifica USER/roles sin dar SELECT a ese login. Consultar `has_function_privilege`, `has_table_privilege`, `has_column_privilege`, `has_sequence_privilege`, `current_user`, membership y PUBLIC y ejecutar negativas reales SQLSTATE `42501`. Repetir carreras admin-wins/effect-wins de config, kill inicialmente ausente y revoke contra POS RC; para ML RR exigir el test separado anterior antes de GO ML. Comprobar que V3 no conserva camino de bypass por wrapper, `search_path` o grants heredados y que un upgrade no cambia hashes V1–V7.
