## Required change

On a successful load, `homeBlocks` is `published.blocks` from `GetHomeUseCase`. Live `home()` always serializes `blocks`. An empty array means no active home sections, and the storefront carousel is that same list (`slice(0, 5)`). The sentence «Este home no tiene bloques para el banner.» is true for that read.

`saveHome` then does `INSERT ... VALUES ('hero', ..., active=true)`. The conflict update changes content and does not clear `active`. A home with no active sections gains a hero block on the first successful publish. `persistHome` still sends `{ title, body }`. The PUT response is `HomeDraft` (title + body, no `blocks`). `mapHomeDraft` leaves `blocks` undefined, and this branch keeps the previous list:

```ts
...(home.blocks === undefined ? {} : { homeBlocks: home.blocks }),
```

`loading` goes back to false and `errorMessage` stays empty, so the template paints the pre-save array again. On the empty-home path that array is `[]`, and the sentence returns. `adminHomeDraft()` already supplies a non-blank default title, so Publicar is enabled while the sentence is showing.

The same keep also leaves an existing hero’s old title and body under the lede «Lo que el home público está rotando.» after Publicar has written the new copy.

Do not paint the sentence, or the old titles, from the pre-save array after a successful publish. Re-read the existing public `GET /content/home` after save, or clear `homeBlocks` to `null` until that read returns. Keep the sentence hidden while that read is loading or in error. Do not assign `homeBlocks` from the console draft: a console `blocks: []` would again claim the banner is empty without a public read. Save stays title + body. No new endpoint, no Kotlin, no invented slides. Add a store test for a public `[]` followed by a save whose body omits `blocks`.
