## After Publicar

Publicar runs `persistHome`. The save executes `{ title, body }` only. When that observable emits, the store calls `publicHome.execute()` again. That use case is `CatalogHttpRepository.readHome()`, which GETs `${apiBaseUrl}/content/home`, so the call is `GET /api/v1/content/home`. A successful response replaces `homeBlocks` from `published.blocks`. It does not copy `blocks` off the PUT body, and it does not keep the array from before the click.

The banner section renders only inside `@if (!state.loading && !state.errorMessage && state.homeBlocks)`. Publicar sets `loading: true` before the save, so the previous list and the empty-banner sentence are not painted while the save and the re-read are in flight.

A failed re-read sets `homeBlocks` to `null` and `errorMessage` from the error. `null` is not a present array, and a non-empty `errorMessage` fails the same `@if`. The sentence «Este home no tiene bloques para el banner.» stays hidden. The form keeps the saved title and body.

## Previous required fix

The store spec `re-reads the public home after save when the save body omits blocks` is on this head. It returns public `blocks: []` on the first read, calls save with `{ title: 'Banner nuevo', body: 'Cuerpo nuevo' }` and no `blocks`, then returns a second public read with the new hero. It expects `publicHome` twice and `homeBlocks` equal to that new hero, with `loading` false and `errorMessage` empty. A public `[]` followed by a save whose body omits `blocks` does not keep the old list.

`homeDraftSavePayload` returns only `title` and `body`. `PUT /user/content/home` sends that object. `mapHomeDraft` leaves `blocks` undefined when the console payload has no array. `loadHome` copies only `draft.title` and `draft.body` into the form and takes the list from the public read. An omitted console field does not become `[]` and does not print the sentence by itself.
