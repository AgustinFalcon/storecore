## Bridge is inside the saga transaction

`commit` and `release` no longer call the bridge from `.also` after `mutateReserved` returns. `mutateReserved` runs under the existing `TransactionTemplate` (`READ_COMMITTED`):

1. `lockVariants` (snapshot, then accounts, products, variants, balances, listings).
2. `lockBalances`.
3. The stock body (commit, release, or expiry).
4. Only if the snapshot says emit: `projectionBridge.requestProjection(variantIds, projectionCause(already))`.

`LegacyBlackStoreProjectionBridge` calls `DesiredStockProjectionUseCase.project` on the injected bean. That method is `@Transactional` `REQUIRED`, so it joins the saga transaction. `JdbcCapabilityService.decide` is also `REQUIRED` (its `REPEATABLE_READ` request does not start a second transaction while the saga one is active). A projector failure marks that same transaction rollback-only. An idempotent replay (`state == already`) returns before the bridge, and the commit test keeps a single `STOCK_DESIRED_CHANGED` row.

`projectionCause` maps `COMMITTED` / `RELEASED` / `EXPIRED` to the three closed `EXTERNAL_BLACKSTORE_*` causes. Any other string becomes `Unknown`, and the bridge returns `NOT_ELIGIBLE` without calling the projector. Empty ids do the same. The bridge does not insert `LISTING_STOCK`.

`expireDue` uses the same `mutateReserved(..., already = "EXPIRED")` and `releaseStock`. Release and expiry are not separate tests in `Dsp009BlackStoreBridgeTest`. The commit test is the one that shows `PENDING` plus `EXTERNAL_BLACKSTORE_COMMIT` and an unchanged historic `LISTING_STOCK` row. The other two causes are the same function and the closed `when`.

## Snapshot before balances, and ML not ACTIVE

`lockVariants` calls `marketplace_ml_sync_snapshot()` first, then locks listing accounts, then `lockInventory` (products, variants, balances, listings ASC). That is the same prefix as `acquireScope`, including the copied “ACTIVE and no live kill” read of the snapshot JSON. `finishReserve` also calls `lockVariants` before `lockBalances`, so a reserve holds the same order even though reserve does not project.

Emit is the snapshot boolean. The bridge runs only when that boolean is true. `DISABLED` (the default the test leaves in place) skips the bridge, commits the POS saga, writes zero `STOCK_DESIRED_CHANGED`, and leaves the historic `LISTING_STOCK` jsonb untouched. `READ_ONLY`, `PAUSED`, `ERROR`, and a live kill take the same skip, because `snapshotAllowsEmit` requires `state == ACTIVE` and zero live kills. The test demonstrates `DISABLED` only.

Reservation `FOR UPDATE` still happens inside the body, after listings. That is later than step 7 of the written global protocol. WEB `acquireScope` locks reservations before balances, but only rows for its own saga key. BlackStore locks its own saga key. Those are different rows, so this does not rebuild the pause-vs-reserve cycle `acquireScope` already fixed. Not a ship blocker for this task.
