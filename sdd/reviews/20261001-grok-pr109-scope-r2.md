## Sealed types

`OrderStatus`, `ShipmentStatus`, `RmaStatus`, `ShipmentTransition`, and `RmaTransition` are Kotlin `sealed class` types. Each known wire is a `data object`. Each type has one `fromWire` translator and an `Unknown` case. The string overloads on `FulfillmentNextAction` are the wire edge: they call `fromWire` and return `transition.wire` or null. `JdbcOrderService` stays on those string overloads, so this PR does not retarget POST.

Stored sets match the existing checks, and hint wires match the existing POST vocabulary:

- Orders: `CREATED`, `PENDING_PAYMENT`, `PAID`, `PAID_STOCK_REVIEW`, `CANCELLED`, `EXPIRED`, `REFUNDED` (V4 check). Only `PaidStockReview` suppresses a hint.
- Shipments: `PENDING` → `PACKED`, `PREPARING` → `SHIPPED`, `SHIPPED` → `DELIVERED`. `DELIVERED`, `CANCELLED`, and `Unknown` have no next action. POST still maps `PACKED` / `SHIPPED` / `DELIVERED`.
- RMA: null → `RECEIVED`, `RETURN_RECEIVED` → `INSPECTED`, `INSPECTED` → `ADJUSTED`. `REQUESTED`, `APPROVED`, `REJECTED`, `CLOSED`, and `Unknown` have no next action. POST still maps `RECEIVED` / `INSPECTED` / `ADJUSTED`.

`FulfillmentNextActionTest` still asserts those HTTP strings, plus cancelled and unknown wires (`CANCELLED`, `IN_TRANSIT`, `REQUESTED`, `RESTOCKED`) and `fromWire` → `Unknown`.

`fromWire` trims. Legal rows are exact check-constraint tokens, and `ResultSet.getString` yields null for SQL NULL, so the read model does not gain a new next action. Blank RMA text would be treated as absent (`RECEIVED`); that value is not a stored `returns.status`.
