## Lock order vs DD-DSP-GLOBAL-LOCK-ORDER

`ChannelProjectionLockOrder.lock` matches `acquireScope` for the tables lifecycle and mapping actually use:

1. `marketplace_ml_sync_snapshot()` first (`FOR SHARE` on action, then config, then switches — V15).
2. `channel_accounts` `FOR UPDATE` for the caller account.
3. `products` by id ASC.
4. `product_variants` by id ASC.
5. Orders, attempts, and reservations omitted. Those callers do not touch those tables. Spec allows the skip.
6. `inventory_balances` ensured then `FOR UPDATE` in ascending `variant_id` (same `INSERT … ON CONFLICT DO NOTHING` then lock as `lockBalance`).
7. `channel_listings` `WHERE variant_id IN (…) ORDER BY id FOR UPDATE`.

`ListingLifecycleUseCase` now reads `variant_id` with no row lock, calls `lock`, then `lockAndSetState` and `project`. `CreateListingMappingUseCase` reads the existing listing variant with no row lock, calls `lock(account, listOfNotNull(new, old))`, then `upsert` and `project`. Listings are no longer taken before products, variants, and balances. That is the pause-vs-`reserveAll` cycle the suite reproduced.

`lockByVariantIds` still uses `FOR UPDATE OF l` only, after the caller already holds the earlier locks in the same `TransactionTemplate`. `project()` joins that transaction (`@Transactional` default `REQUIRED`). It does not open a second lock ladder.

## Judged candidates that are not P0/P1

- **Snapshot more than once.** `decide` runs before `lock`, `lock` calls `marketplace_ml_sync_snapshot()` again, and `project` calls `decide` again. All three are the same `FOR SHARE` function in one transaction. Re-entry does not upgrade to `FOR UPDATE` and does not wait on locks this transaction already holds. Same note prv35 accepted for `project` after `acquireScope`.
- **`upsert` has no `FOR UPDATE`.** `lock` already holds `FOR UPDATE` on listings for the discovered variants. `upsert` then updates that row. Putting `FOR UPDATE` back before `lock` would restore the deadlock. `lockAndSetState` still locks by listing id, after `lock`, so a stable variant is already in the ordered set.
- **Variant changes between the unlocked read and `lock`.** Spec discovery is optimistic. If another remap commits a different variant first, `lockAndSetState` / `upsert` can lock that listing id outside the ordered set. Spec text prefers rollback and retry when candidates change. `project` does not take product or balance locks after that (`FOR UPDATE OF l` only), and `acquireScope` still takes the account before listings, so this window does not rebuild the pause-vs-reserve cycle on a stable variant. The failing test passed after the follow-up. Not a ship blocker for this change.
- **Caller account only.** `acquireScope` locks every account that has a listing for the variants, sorted. This helper locks the caller account, still before products and listings. The subset holder does not wait for the other account. Not an inversion with inventory.
