## Implementation

`JdbcEffectivePriceQueryAdapter.findBySkus` is the only price reader added by this commit. For each SKU it loads `products.base_price` and one offer row:

- `offers` joined through `offer_products` on `product_id`
- `o.status = 'ACTIVE'`
- `CURRENT_TIMESTAMP BETWEEN o.starts_at AND o.ends_at`
- product and variant still active
- `ORDER BY o.priority DESC, o.id ASC LIMIT 1`

`PERCENT` is `base * value / 100` at scale 2, half up, capped by base. `FIXED` is capped by base. Anything else discounts zero. `effective = base - discount`. `offerRef` is the offer id string. `campaignRef` is the offer name. The SQL does not read `channel_price_policies`.

Public `GET /api/v1/catalog` still filters `offers=true` with `EXISTS` on `offer_products` / `offers` (`ACTIVE` and `now() BETWEEN starts_at AND ends_at`). In PostgreSQL `now()` and `CURRENT_TIMESTAMP` are the same transaction timestamp, and the outer query already requires `p.status = 'ACTIVE'` and `v.active`. The card price, `originalPrice`, and `offerRef` then come from the port. `originalPrice` is the base only when `discountAmount > 0`.

`GET /api/v1/catalog/products/{sku}` uses the same port for `price.effective` and `offerRef`. With no snapshot it keeps the row base and a null offer. The ended-offer test sees effective 100 and `offerRef` null.

Cart add (`JdbcCartService.price`) no longer has its own offer SQL. It reads the same port, rejects a missing or inactive SKU, and snapshots `offer_id` via `offerRef.toLongOrNull()` plus `campaignRef`. Checkout still uses the stored cart line. That matches the baseline rule that the cart snapshots price before checkout.

The card image is the first `product_images` row by `sort_order, id`. `saveProduct` already inserts only `https://` URLs, and the new test asserts that URL. There is no second `https` predicate on the read.

## Architecture

| Check | Result |
| --- | --- |
| Domain | `EffectivePrice` is a pure Kotlin data class. No Spring, JPA, or JDBC. |
| Port | `EffectivePriceQueryPort` lives in `commerce.application.port.output`. |
| Adapter | `JdbcEffectivePriceQueryAdapter` is `@Repository`, implements the port, same `storecore.identity.enabled` gate as catalog and cart. |
| Dependency direction | `JdbcCatalogService` and `JdbcCartService` inject the port. They do not reference the adapter class. |
| Discount formula | The arithmetic sits in the adapter. That matches existing commerce JDBC services. The domain type stays a snapshot. |
| Pre-existing | `JdbcCatalogService` still depends on the concrete `JdbcInventoryService`. This commit does not add that coupling. |

Catalog and cart **do share** `EffectivePriceQueryPort`. One adapter bean serves search, product detail, and cart add.

`/user/promos` **is still unbridged**. `PromoController` and `JdbcPromoService` are unchanged. `save` inserts `channel_price_policies` with `writer_kind = MANUAL` and does not insert `offers`. The new adapter never selects that table. `CommerceHttpIntegrationTest` still expects `COUNT(*) FROM offers` to stay 0 after a manual promo named `manual-$sku`. Desired and observed on the catalog price object stay null.

Admin catalog save still prefers `price.base` over `price.effective`. The user-catalog form edits base and only displays effective. This commit does not write the discounted amount back into `products.base_price`.
