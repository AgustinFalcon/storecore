## Cambios requeridos

1. **Una sola secuencia de lock, también en Tx-A/Tx-B y en commit/release.** El spec técnico todavía dice que Tx-B empieza en `SELECT FOR UPDATE` de la saga, y más abajo que el orden único es advisory lock → saga → `inventory_balances`. AC-STK-3 pone el advisory lock dentro de Tx-B; ADR-007 y PIC-004 lo exigen antes del chequeo de tombstone de Tx-A y otra vez en Tx-B. AC-STK-4 y los criterios de TASK-PIC-005 no dicen que commit/release tomen ese lock y consulten el tombstone antes de resolver la saga. Alinear spec funcional, el párrafo Tx-A/Tx-B, Locks (P1), data model y criterios de PIC-005 con ADR-007.

2. **No colapsar `OPERATION_STATE_CONFLICT` con el CONFLICT reintentable.** La tabla “Recuperación GET (única tabla)” no tiene fila para ese código; la fila (h) sigue diciendo re-POST de la misma cuádruple. AC-STK-7 dice `retryable=false` y no re-POST. Agregar la fila y describir ese comportamiento en `ConflictReserve` / `ConflictCommitRelease` del OpenAPI (el enum ya lo incluye; la prosa no).

3. **Ownership V4/V5/V6 dentro del delta.** ADR-008 y las tasks separan V4=`PIC-001`, V5=`PIC-002`, V6=`PIC-010`. `data-model-v1.md` sigue siendo un solo script SQL: el comentario marca sólo el INSERT de V4, el JSON de trece números no se llama schema v2, y no hay corte V5 ni una nota de que V6 no vive en ese SQL. Partir el diseño (no ejecutable) en esos tres dueños y nombrar el config como schema v2, sin SQL de `changeState` con `{}`.

4. **Retarget del PR a `master`.** Hasta que la base de GitHub sea `master`, el PR publicado no es docs-only.
